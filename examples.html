The boot-time ring3 process

Before the shell even shows its first prompt, a real minicc-compiled MiniC program (not hand-assembled) has already been loaded into its own isolated address space and started running in ring 3, preemptible by the timer like any other task. The two hello from a LOADED process! lines are printed from inside that loaded, executing code via a real int 0x80 syscall — a message that lives inside the loaded blob itself, not a kernel string.

handle 0 (self) -> taskIndex 0x7 is the process resolving its own well-known handle all the way through the kernel object table to real ground truth — 0x7 is exactly what ps independently reports for this same process later, meaning two completely different code paths (a ring3 syscall's handle lookup, and the shell's direct table read) land on the identical number. handle 99 (invalid) — never allocated — comes back as the same -1 sentinel every failure path uses, not garbage or a crash.

The File.write()/File.read() and POSIX lines are the native API and the POSIX shim, both exercised from inside that same ring3 process — real obj.method() calls (msgFile.write(...)) and real free-function calls (write(fd, ...)) wrapping two different syscalls, not raw syscall numbers either way. The two separate POSIX read() lines return two different, correct slices of the same underlying buffer — proof the position cursor genuinely advances between calls, not just replaying the whole buffer each time.

Channel.open() ok=0x1 and unauthorized Channel.send() succeeded=0x0 are the real capability/rights proof. open() turns a raw channel index into a real handle — but the kernel's own policy only ever grants that handle receive rights, never send rights. The very next line deliberately attempts to send through that exact handle anyway — and succeeded=0x0 (false) is the actual point: without real per-handle rights enforcement, checked before the underlying channel is ever touched, this call would have silently succeeded. The receive that follows later in the session, through that same handle, still works normally — the restriction is real but not overzealous.

Heap & frames

Two allocs land exactly where hand arithmetic predicts; free then mem shows the byte given back matches exactly. frames' count is built entirely from parsing the real multiboot memory map at boot — not a made-up number.

Paging

map proves the whole dynamic-paging chain end to end: a physical frame beyond the multiboot memory map's low end, mapped at a virtual address a full 1GB past anything the boot-time static map set up, written through and read back correctly — real PML4/PDPT/PD/PT walking and on-demand table creation, not just "an address came back."

Scheduler

tasks proves both preemption and blocking in one line. Two purely cooperative tasks stay in exact lockstep. A third — a tight loop that never calls yield() at all — runs six orders of magnitude ahead, because it spins its entire timer slice every turn instead of giving up the CPU voluntarily; only possible if the timer genuinely forces control away from it periodically. A fourth, sleeping between increments, tracks ticks / interval almost exactly — proof sleep() really removes a task from the round-robin for that long, not a no-op.

Process isolation

procs: two tasks map the identical virtual address in their own private address space to their own physical frame, and each keeps reading back its own distinct constant forever. The @phys addresses being genuinely different is the real proof — not just "two different numbers came back," but that the same virtual address resolves to two different physical frames depending on which address space is asking, exactly what isolation has to mean.

IPC

The first two chan reads, with an arbitrary number of other commands run in between, show a receiver task genuinely still blocked on an empty channel — not a short timeout, not a no-op. send calls the kernel-side channelSend() directly from the shell's own context; the instant it succeeds, the next chan shows the exact value, and the receiver (an isolated process with its own private address space) woke up on its own. The message genuinely crossed from one isolated address space to another through the channel, not shared memory.

Disk & filesystem

disk reads back an exact signature written from the host side before the kernel ever booted — real reads against independently-verifiable content. diskwrite writes a distinct 256-value repeating byte pattern and reads it straight back, reporting a byte-exact match — proves the write path independently of the read path. mkfs/mkfile/cat creates two files back to back and reads each one back correctly and distinctly, even after the other exists — no cross-file clobbering, and reads are always fresh from disk, never a cached copy.

VFS

vfscat /system/file0.mfs and vfscat /devices/ticks back to back is the actual point of the VFS layer: the identical function call reaches two completely different mechanisms — real disk I/O vs. live kernel state, no disk touched at all — depending only on the path prefix.

Process spawning from disk

install writes the kernel's own compiled-in test program out to a real file (the byte count is the real, host-verifiable size of that compiled-and-flattened blob). spawn reads it back and launches an independent second process — ps afterward shows two real processes with genuinely different cr3 values, confirmed from the kernel's own bookkeeping.

A ring3 process spawning itself

ring3go takes a completely different path from install/spawn above: instead of the shell (kernel mode) launching a process, it wakes the boot-time ring3 process's own blocking Channel.receive() syscall — a real ring3 process blocking itself on a syscall for the first time in this kernel's history. Once it wakes, it calls Process.spawn() itself:

The last fourteen lines are the spawned child — the exact same program, running its own _start() from scratch in its own freshly cloned address space, with its own distinct task index (0x9, not the parent's 0x7) and its own independent handle table — its Channel.open() call gets a brand-new handle, resolved through its own table, never the parent's. It reaches its own Channel.receive() too, but the single-slot mailbox is already empty again (the parent's own receive() consumed the one message ring3go sent) — so it just blocks there forever, never reaching its own Process.spawn() call. That's what stops this from spawning a second, third, fourth generation automatically: no recursion-guard flag needed, just the mailbox's own single-slot semantics.

(The child's own File.write() shows the "already exists" failure sentinel here rather than a fresh byte count — the parent already wrote that same file earlier in this same boot, and MiniFS correctly refuses to overwrite an existing file. File.read() still succeeds, reading back the real, persisted content either way.)
