Architecture

How MiniC OS is built

Almost everything past the boot transition is ordinary MiniC. The only hand-written x86 assembly is what's genuinely below what a MiniC function body (asm("..."), no operand binding, can't reach a local variable) can express: program structure, not logic.

Boot process

Multiboot1 drops the kernel in 32-bit protected mode; MiniC only targets x86-64. Getting from one to the other — loading a GDT, building page tables, enabling long mode, far-jumping into a 64-bit code segment — is hand-written in boot/boot.s, the same way every kernel project does it, even ones written in Rust or Zig. boot/linker.ld places the multiboot header and code at the conventional 1MB load address multiboot expects.

boot.s also owns the GDT/TSS setup: a ring3 code/data segment pair alongside the ring0 ones, and a TSS whose RSP0 field tells the CPU which stack to switch to on any ring3→ring0 transition. RSP0 is an absolute reset point, not a continuation — the CPU loads it fresh on every transition, so pointing it at a stack something else is still using silently corrupts that other thing's state. boot.s sets it once, to its own dedicated stack, as a safe initial value; from the process model onward (see below), the scheduler repoints it per-task on every context switch instead.

Once in 64-bit mode, boot.s calls MiniC's own entry point, _start() in kmain.mc — everything past that point is ordinary MiniC, using nothing the language's freestanding/ systems phase didn't already build (volatile, packed struct, pointer arithmetic, and asm(...) for the handful of raw instructions MiniC has no other way to express: out/in/lidt/sti/ invlpg, reading cr2/cr3).

Memory map

RegionWhat's there
0 – 1GBthe boot-time static identity map (boot.s's own page tables) — kernel code, stack, heap, and every demo command's memory all live here, shared and mapped identically in every address space (PDPT[0]/PDPT[1])
0x80000000+ (PDPT[2] and up)each process's private region — not present by default in a freshly cloned address space, populated on demand only by whichever task owns that PML4. This is where a loaded ring3 process's own code/data (0x80000000) and user stack (0x80020000) live.
As of milestone 26, a cloned (ring3-capable) address space's copy of PDPT[0]/PDPT[1] has the user bit stripped — a ring3 process can no longer read/write/execute this region directly, only through a syscall (which raises CPL to 0 first). See Memory protection below.

Scheduler

A fixed table of tasks, each with its own kalloc'd stack. createTask() hand-builds a new task's initial stack to look exactly like what the hand-written switch_context() would have left behind, with the task's entry point as a fake "return address" — the first switch into a never-run task lands there via an ordinary ret, no special-casing needed for "first run" vs "resuming."

yield() round-robins to the next non-blocked task — called voluntarily by cooperative tasks, and also called from inside the timer interrupt handler, which is what makes scheduling preemptive: since the interrupt handler is just an ordinary nested MiniC call on whichever task's stack the CPU happened to interrupt, calling yield() from inside it suspends that call exactly like a voluntary yield() would.

sleep(ticks) adds real blocking: a task marks itself blocked with a wake tick and yields away; the scan skips blocked tasks, waking one up the moment its condition is met. Channel receive (see IPC below) reuses this exact mechanism with a second kind of wake condition, not a separate blocking primitive.

Process model & isolation

Real per-process address-space isolation: cloneAddressSpace() builds a fresh PML4 whose entry 0 points at a fresh PDPT that shares PDPT[0]/PDPT[1] (identity map + heap) with the kernel's own PDPT — literally the same physical sub-tables, so kernel code/stack/heap stay reachable unchanged — while everything from PDPT[2] up starts out not-present, private to whichever task gets that PML4.

spawnProcess(imageStart, imageEnd, loadVaddr, stackVaddr) is the real loader: clones a fresh address space, maps and copies a byte range into it page by page, maps a user stack, then creates a scheduler task whose kernel-mode entry does exactly one thing — enter ring3 at the loaded address via a hand-written fake-iretq-frame trick. From then on the task only ever runs in ring3, preemptible by the timer like any other task. spawnProcessFromPath(path, ...) is the same loader fed from a real file read through the VFS instead of a pointer range.

A kernel-wide KernelObject table plus a separate per-process handle table give ring3 code a small integer instead of a raw kernel pointer — resolveHandle(processIndex, handle) is the one place that integer becomes a real object index, bounds- checked and existence-checked, never trusted directly. Every process gets a handle to itself for free, guaranteed to land in the well-known slot 0 (a fresh handle table starts empty, so the first allocation into it always takes slot 0).

IPC (channels)

A Channel is a single-slot mailbox (one u64 message). channelSend() is non-blocking — fails outright if the mailbox is already full, rather than overwriting an unread message or blocking the sender too (a real, separate hard problem, not tackled yet). channelReceive() is the one genuinely new scheduler mechanism: it blocks the calling task exactly the way sleep() already does, just with a channel index set instead of a wake tick — the blocked-task scan gained a second wake condition (a message arriving) alongside the tick check.

The ring0/ring3 boundary & syscall ABI

The calling convention is this kernel's own, since it goes through a software int 0x80 gate rather than the fixed SYSCALL/SYSRET convention: rax = syscall number in / return value out, rdi/rsi/ rdx = up to three arguments.

A syscall runs with the calling process's own address space still loaded (no CR3 switch on int 0x80 entry), so dereferencing a ring3-supplied pointer needs no special mechanism — but nothing here validates that a pointer argument actually belongs to the calling process (handle arguments are now rights-checked for both Channel and Process, as of milestones 25 and 27 — see Capabilities below). Capabilities & rights

Every Handle carries a rights bitmask, set once when the handle is granted and never widened afterward: 

const int RIGHT_QUERY = 1;
const int RIGHT_SEND = 2;
const int RIGHT_RECEIVE = 4;

openChannel (syscall 9) is the one place a ring3 process can turn a raw channel index into a handle — and the one place the kernel decides policy: it always grants RIGHT_RECEIVE only, regardless of what the caller might want, since nothing in this kernel today needs a ring3-initiated send (the shell always sends directly, in kernel mode). channelSend/ channelReceive check the calling handle's rights before ever touching the underlying channel — a handle obtained through openChannel genuinely cannot be used to send, not just "isn't expected to." See the Walkthrough for a real rejected send attempt.

Milestone 27 extended real enforcement to Process handles too. RIGHT_QUERY had existed since milestone 25 and was already granted to every process's own self-handle (since milestone 14) — but syscall 3 never actually checked it, resolving any valid OBJ_PROCESS handle regardless of rights. Now it does, using the same inline check syscalls 7/8/9 use. openProcess (syscall 10) is the first real cross-process capability — given another task's index, it mints a handle to that process in the caller's own table, granting the intersection of a caller-requested rights bitmask and what's actually grantable. Requesting 0 still returns a real, valid handle — just one that can do nothing, which is what the negative-space proof actually exercises: a handle opened with no rights genuinely fails to query, while a second handle to the same process opened with RIGHT_QUERY succeeds and reports the correct taskIndex. See the Walkthrough for the real captured proof.

Memory protection: the shared region, and NX

Milestone 26 closed a real gap: cloneAddressSpace() (mm/paging.mc) used to copy the kernel's own PDPT[0]/PDPT[1] entries into every new address space unchanged, including the user (0x04) bit — since x86 paging ANDs that bit across every level from PML4 down to the leaf, a supervisor-only leaf mapping underneath didn't matter if an intermediate PDPT entry above it was user-accessible. Tracing every actual leaf-level mapPage/mapPageIn call site first showed the real, exploitable surface was narrower than it looked — the heap and the map demo command already passed leaf flags without the user bit, so the actual gap was specifically boot.s's static 1GB identity map's 2MB huge-page leaves (PDPT index 0).

The fix strips the user bit from the copy cloneAddressSpace() makes — boot.s's own tables and the kernel's original address space (gPML4Phys, used directly by plain kernel tasks that never enter ring3) are untouched. Every legitimate ring3 interaction with this region already goes through a syscall, which raises CPL to 0 before touching kernel memory or the heap — nothing in this kernel needed direct ring3 access to begin with.

Verified with a genuine negative-space proof, not just a topology change: the shell's ring3fault command sends a second trigger value on the existing ring3-demo channel, causing the boot-time process to deliberately attempt a forbidden write to 0x100000 (the kernel's own multiboot load address — present, and never mapped by that process itself). The existing page-fault handler reports the exact faulting address and halts, before the process's own "it worked" print can ever run. See the Walkthrough for the real captured output.

Milestone 28 added real NX (no-execute) enforcement — the classic W^X hardening that stops injected "shellcode" from being jumped to and run. boot.s sets EFER.NXE (bit 11) at boot, in the same rdmsr/ wrmsr round trip as the existing EFER.LME — order matters, since setting a page table entry's NX bit (PTE bit 63) before NXE is live is a reserved-bit violation on every access to that page, not an execute-only restriction. Unlike the "user" bit above (which the CPU ANDs across every translation level, so an intermediate PDPT entry had to be fixed), the CPU ORs the NX bit across every level — only the final leaf PT entry ever needs it set, no intermediate-table change required. Applied to every dynamically-mapped region that's genuinely pure data: the heap, the map demo, the scheduler's private demo mapping, and — the real point — every ring3 process's own user stack. Deliberately not applied to a loaded ring3 program's own code+data image: the loader still flattens a whole compiled program into one contiguous blob with no tracked code/data boundary (see Compiled MiniC in ring 3), so a real W^X split within a loaded image remains open — see Known limitations.

Verified with a real negative-space proof again: the shell's ring3nx command has the boot-time process write a real ret opcode (0xC3) onto its own stack and attempt to call it. The page fault's error code — 0x15 — has the CPU's own instruction-fetch bit (bit 4) set, independently distinguishing this from ring3fault's own write-violation error code (0x7). See the Walkthrough for the real captured output.

The native API

Ring3 processes are real, minicc-compiled MiniC programs (see below), and the native API is real obj.method() syntax wrapping the syscalls above — not raw syscall numbers.

File — whole-file, path-based (no open/close/seek at the kernel level)

u64 File.read(File* self, char* buf, u64 maxLen);

The POSIX-shaped shim

open/read/write/close — plain free functions, deliberately not methods, matching POSIX's real API shape rather than extending the native OO-style one. Implemented entirely in ring3 MiniC, with no new syscalls and no kernel changes: since File is whole-file only, open() loads (or starts) a per-fd in-memory buffer once, read()/write() serve out of it while advancing a position cursor, and close() flushes a written buffer through File.write() in one shot. 

int open(char* path, int mode);   // 0 = read, 1 = write (create)
int read(int fd, char* buf, int len);
int write(int fd, char* buf, int len);
int close(int fd);
A real, small gap from true POSIX: only one open-for-write "session" can safely target a given path at a time — there's no kernel-side file-descriptor concept backing this, just a per-process in-memory table.

Compiled MiniC in ring 3

Ring3 programs are real, minicc --freestanding-compiled MiniC — not hand-assembled machine code. The loader's model is dead-simple (copy one contiguous byte range, jump to its first byte), which doesn't survive unmodified for compiled output: string literals land in .rodata and globals in .bss/ .data, separate ELF sections that a normal multi-object link would scatter apart. Fixed with a build-step, not a compiler-level, change: the ring3 program gets its own standalone link (proc/ring3.ld, every section placed contiguously) and gets flattened with objcopy -O binary before being embedded — the loader itself never changed.

asm(...) has no operand binding, so a syscall's arguments can't be received in a register and used immediately — a small doSyscall(num, arg1, arg2, arg3) helper stages them into globals first, then one asm(...) block loads them into rax/rdi/rsi/rdx right before int 0x80.

Hardware discovery: PCI

Milestone 29 (Phase X's first step) is the first time this kernel discovers its own hardware instead of trusting a fixed, hardcoded I/O port — every earlier driver (VGA, serial, keyboard, PIT/PIC, ATA) just assumes its device sits at a well-known legacy address. That stops working the moment a device's location genuinely isn't fixed, which is exactly true of a NIC — networking's real prerequisite. drivers/pci.mc walks the legacy CONFIG_ADDRESS/CONFIG_DATA mechanism (I/O ports 0xCF8/0xCFC, drivers/ io.mc's new 32-bit outl/inl — PCI config space is dword-addressed) across all 32 device slots on bus 0, checking function 0 of each and only probing functions 1–7 for devices whose header-type byte marks them multi-function.

Deliberately scoped to bus 0 only — no recursion through a PCI-to-PCI bridge's secondary bus, since QEMU's default machine has none. A real bus walk would read a bridge's own secondary-bus-number register and recurse; that's a genuine but separate extension for whenever a device beyond bus 0 needs finding, not tackled here. There's also no general driver-registration/probe framework yet — finding a device by vendor:device ID today means a caller manually scanning gPciDevices[].

Verified against something this kernel had no part in choosing: QEMU's own default machine model. Every device pci finds is a real, publicly-documented vendor:device ID pair — 0x8086:0x1237 (the i440FX host bridge), 0x8086:0x7000/0x7010/0x7113 (PIIX3 ISA bridge / IDE controller / PIIX4 ACPI bridge — 0x7010 is literally the same IDE controller disk/ata.mc already talks to by hardcoded port), 0x1234:0x1111 (the Bochs/QEMU standard VGA device), and 0x8086:0x100e — a real Intel e1000 gigabit NIC, found with zero extra QEMU flags, and the next Phase X milestone's target device. See the Walkthrough for the real captured output.

The e1000 NIC driver

Milestone 30 is a real driver for the e1000 milestone 29 already found — deliberately scoped to initialization only: enable the device, map its registers, read back real hardware state. Setting up the RX/TX descriptor rings and moving an actual packet is a separably-sized hard problem, left for a later milestone — the same "narrowest safe first version" discipline bus-0-only PCI enumeration used.

Unlike every earlier driver in this kernel, the e1000's real register file isn't reached through port I/O — it's memory-mapped (MMIO). net/e1000.mc enables the device over PCI (drivers/pci.mc's new pciConfigWriteDword() — this kernel's first PCI config space write, every earlier use was read-only — sets Memory Space + Bus Master in the command register), reads BAR0 (pciReadBar0()) to find the device's real physical MMIO base, and maps 8 pages of it into the kernel's own address space via mm/paging.mc's ordinary mapPage() — the first time this kernel has mapped device registers rather than RAM, though the mapping mechanism itself doesn't distinguish the two.

A real assumption worth stating plainly, since it's the kind of thing that would fail badly and confusingly if wrong: BAR0 has to already hold a valid, assigned physical address for this to work at all. It does, because QEMU's -kernel boot still runs SeaBIOS first — multiboot loading is one of SeaBIOS's own jobs, not a BIOS bypass — so real PCI bus enumeration and BAR assignment already happened before this kernel ever got control. Confirmed empirically rather than assumed: a genuinely unassigned BAR would have meant mapping physical address 0 or garbage, and the driver would have read back nonsense instead of a real MAC address.

The MAC address comes straight from RAL0/RAH0 — pre-loaded by QEMU's own emulated EEPROM at power-on, the same way real hardware auto-loads its burned-in address — rather than implementing the separate EEPROM-read protocol (register EERD) just to re-derive a value already sitting in plain registers. Verified the same way milestone 29's own proof was: checkable against something this kernel had no part in choosing. The real MAC read back, 52:54:00:12:34:56, is QEMU's own well-known, publicly documented default NIC MAC — not a number this driver could fake its way into producing by accident — and the link-up bit reads a second, separate piece of real hardware state. See the Walkthrough for the real captured output.

Milestone 31 builds on that groundwork with real TX/RX descriptor rings and a genuine packet round trip — the DMA-buffer-management work milestone 30 deliberately deferred. A NIC doesn't move bytes through registers one at a time the way port I/O devices do: the driver hands the hardware a ring of descriptors (each a pointer to a real data buffer, plus length/status/command fields) living in ordinary RAM, and the device DMAs to/from those buffers itself once bus-mastering is enabled (already turned on in milestone 30). packed struct TxDescriptor/RxDescriptor match the hardware's own 16-byte layout exactly. e1000Send() copies data into a buffer, hands a descriptor to the hardware, and polls the descriptor's own DD (descriptor done) status bit — the hardware's own confirmation it genuinely completed the transmission, the same bounded-poll, fail-clean discipline disk/ata.mc's ataWaitReady/ataWaitDrq already established. e1000Receive() is the RX-side equivalent.

Deliberately not a real ARP subsystem — no address resolution cache, no general request/reply handling. The shell's new arp command crafts exactly one hardcoded, valid Ethernet+ARP request frame asking "who has 10.0.2.2" (QEMU's SLIRP networking's own well-known default gateway), purely as a real external stimulus to prove RX genuinely works — the same "one hardcoded test case, not a general framework" scope milestone 26's ring3fault already used.

A real fix found during testing, not assumed correct from the start: the first attempt's RX poll used a raw instruction-count spin bound, and got back nothing. Not a driver bug — a measurement one. A tight spin loop doesn't reliably correspond to any particular amount of real wall-clock time, and a genuine external SLIRP round trip needs real time to happen. Fixed by polling against isr/isr.mc's own gTickCount instead of a raw iteration count — the same underlying lesson this project's QEMU/TCG timer-rate gotcha already taught, applied to a new context.

Verified with the strongest proof this driver has produced yet: TX confirmed by the hardware's own descriptor-done bit, and RX confirmed by a genuine reply from QEMU's real, external network stack. from=52:55:0a:00:02:02/senderIp=10.0.2.2 are QEMU's own documented default gateway MAC/IP — not anything this kernel could have fabricated. See the Walkthrough for the real captured output.

A real ARP resolver

Milestone 32 replaces milestone 31's own hardcoded one-shot ARP request/reply with a genuine resolver, built directly on the proven TX/RX plumbing rather than starting over. net/arp.mc keeps a fixed-size cache (ArpEntry[8]) and exposes one real entry point, arpResolve(ip, macOut): check the cache first; only on a miss, send a real request and poll for a genuinely matching reply (right EtherType, right opcode, right sender IP — anything else that arrives is ignored, not mistaken for the answer) against a real gTickCount-bounded timeout, the same lesson milestone 31 already learned about spin counts not reliably corresponding to real time.

Deliberately scoped as a client (resolver) only, not a responder — this kernel has no assigned IP address of its own in any real sense yet (no DHCP, no static configuration), so answering "who has <our address>" doesn't mean anything until it does. The cache also has no eviction or TTL — a fixed-size table that just fills up, the same "narrowest safe first version" every driver-layer milestone in this phase has used.

The shell's arp command (same name milestone 31 used, now backed by the real mechanism) runs four checks in one pass, each independently checkable: resolve the gateway (a real external round trip, non-trivial elapsed ticks); resolve it again (zero elapsed ticks — a real, timing-based proof of the cache, not just "the same answer twice"); resolve a second, different real address (QEMU SLIRP's own DNS proxy, 10.0.2.3 — proving the resolver genuinely generalizes); and resolve an address nothing answers for (correctly returns false after the real timeout, not a hang). See the Walkthrough for the real captured output.

Testing methodology

Every claim in this project is backed by a concrete, checkable assertion — never just "it didn't crash." An exact byte count matching hand arithmetic, a register value read back and printed (proving real CPL 3, not just "a syscall happened"), a physical address that genuinely differs between two isolated processes mapping the identical virtual address, a frame-allocator count identical before and after an operation that must not leak. See the Walkthrough for what these look like in practice.

Testing runs in QEMU, headless, with serial output redirected to a file and keystrokes sent over the monitor socket: 

qemu-system-x86_64 -kernel kernel.elf -display none \
    -serial file:serial.log -monitor unix:/tmp/qmon,server,nowait \
    -drive file=disk.img,format=raw,if=ide -no-reboot
echo 'sendkey h' | nc -U /tmp/qmon   # types 'h'
echo 'sendkey spc' | nc -U /tmp/qmon # space
echo 'sendkey ret' | nc -U /tmp/qmon # enter

Known limitations (on purpose, for now)

  • The shared identity-map/heap region is still fully user-accessible — fixed in milestone 26: a cloned address space's copy of PDPT[0]/PDPT[1] has the user bit stripped, verified with a real forbidden-write page fault (see Memory protection). Real isolation now covers both the private per-process region and direct ring3 access to the shared one — everything ring3 code still legitimately needs there goes through a syscall instead.
  • Pointer arguments (paths, buffers) are checked for validity/bounds but not ownership — nothing stops a ring3 process from passing a pointer that doesn't actually belong to it. Both Channel (milestone 25) and Process (milestone 27) handles are now real, rights-checked capabilities (see Capabilities & rights) — but Process only has one real right (RIGHT_QUERY) to enforce so far, since there's no second Process operation (like a real terminate/kill) yet to need a second one.
  • No process teardown/exit exists at all. A ring3 process, once launched, runs forever (or blocks forever) — there's no syscall to end one, and a spawned process's frames are never freed.
  • No NX (no-execute) enforcement anywhere — fixed in milestone 28 for every dynamically-mapped pure-data region, including every ring3 process's own user stack (see Memory protection). Still open: a loaded ring3 program's own code+data image stays entirely executable — the loader flattens a whole compiled program into one contiguous blob with no tracked code/data boundary, so a real W^X split within a loaded image is a separate, larger problem. ASLR and true process sandboxing (beyond the address-space isolation that's existed since milestone 12) remain two more genuinely different, completely unscoped mechanisms — not silently forgotten, just not yet tackled.
  • Every fixed-size table in this kernel (tasks, processes, objects, handles, channels, mounts) has a small, arbitrary capacity, and most creation calls at boot don't check their own return value for success — harmless today (nothing is near its cap), a real bug class once boot-time setup grows further.
  • MiniFS is deliberately simple — flat namespace (no directories), a fixed 16-file cap, no delete/truncate/append, no journaling (a crash mid-write leaves partial state), and files can't safely be overwritten (only created fresh).
  • The ATA driver only supports the primary bus's master drive, polling rather than interrupt-driven — no secondary bus, no slave, no AHCI/NVMe.
  • No PCI enumeration — fixed in milestone 29 for bus 0 (see Hardware discovery: PCI). Still open: no bridge recursion beyond bus 0, no general driver-registration framework. disk/ata.mc also hasn't been retrofitted to use PCI discovery instead of its own hardcoded 0x1F0, even though pci now finds that exact same controller.
  • No NIC driver, no packet TX/RX — both fixed as of milestones 30-31 (see The e1000 NIC driver): the e1000 is PCI-enabled, MMIO-mapped, and moves real packets through real TX/RX descriptor rings, verified with a genuine external round trip through QEMU's own network backend. No real ARP subsystem — fixed in milestone 32 (see A real ARP resolver): a genuine cache, arpResolve() for any target address. Still fully open: ARP is client-only (this kernel never answers "who has our address" — it has no real IP configuration of its own yet), the cache has no eviction/TTL, and no IP, no UDP/TCP — the entire protocol stack above ARP remains ahead, each realistically its own future milestone. The rings are fixed-size (8 descriptors each), and both TX/RX poll rather than using the device's own interrupt capability — the same "poll first, interrupts later" precedent disk/ata.mc already established.
