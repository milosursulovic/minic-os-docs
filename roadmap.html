Roadmap

Every milestone, in order

Each milestone below was scoped as one hard problem, proven with a concrete assertion in QEMU, then shipped — not designed far in advance. The long-term architecture (a UNIX namespace/shell + NT-style kernel objects/handles + microkernel-ish IPC/service isolation + a capability security model, exposed through a native MiniC API with a POSIX compatibility layer on top) is planned in phases, each becoming a real numbered milestone when its turn comes.

Milestones 1–10: the foundation

  • 1: boot to 64-bit long mode + VGA text output done — a multiboot1 image boots in QEMU, transitions from 32-bit protected mode into 64-bit long mode, and writes to the VGA text buffer directly from ordinary MiniC. The 32-to-64-bit transition is hand-written in boot/boot.s — below what asm(...) can express, same as every kernel project. Everything past that point is MiniC.
  • 2: real interrupts done — an IDT built as an ordinary MiniC array of packed struct entries, the 8259 PIC remapped, the PIT reconfigured to ~100Hz, working timer + keyboard handlers.
  • 3: heap + a minimal shell done — a bump allocator over the identity map, plus an interactive shell built on the keyboard handler's line buffer.
  • 4: a real free-list heap done — kalloc splits blocks, kfree coalesces adjacent free ones forward.
  • 5: two-way coalescing + a physical frame allocator done — kfree coalesces backward too, and a frame bitmap allocator is built from the multiboot memory map.
  • Language cleanup done — five milestones of real kernel code surfaced six genuine MiniC language gaps (char literals, char arithmetic, a rigid sizeof, no break/continue, array decay stopping short of void*, extern restricted to functions) — all fixed as real compiler features in the minic repo.
  • 6: real dynamic paging done — walks/creates a full PML4→PDPT→PD→PT chain of 4KB pages on demand, so the kernel can map memory anywhere, not just inside the static identity map.
  • 7: a frame-backed, dynamically growing heap done — the heap grows a chunk at a time as the free list runs dry, instead of a fixed reservation.
  • 8: a cooperative scheduler done — a hand-written context switch, a fixed table of tasks each with its own stack, round-robin via voluntary yield().
  • 9: preemptive scheduling done — the timer interrupt now forces a task switch, not just voluntary cooperation.
  • 10: real task blocking via sleep() done — a task can step out of the round-robin for a given number of ticks.

At this point everything still ran in ring 0, sharing one page-table hierarchy — "tasks" were kernel threads, not isolated processes. The long-term architecture plan was settled here, and every milestone since has been a real numbered step toward it.

Phase I–V: ring 3, isolation, the object model, IPC

  • 11: ring 3 + syscalls done — the first real ring0/ring3 privilege boundary: a GDT ring3 code/data pair, a TSS (RSP0 on its own dedicated stack), and an int 0x80 syscall gate (DPL=3) with a minimal dispatcher. Address-space isolation deliberately deferred — proving the privilege-transition mechanism itself came first. Verified by reading back cs=0x1B from inside ring3 (real CPL 3, not just "a syscall happened").
  • 12: per-process address spaces done — real address-space isolation: each task can get its own PML4, with a private region no other task can see even at the identical virtual address. Verified: the same virtual address genuinely resolves to two different physical frames depending on which address space is asking.
  • 13: a real Process concept + a loader done — wires ring3/syscalls and per-process address spaces together: a loader copies a byte range into a freshly cloned private address space and schedules it as a genuinely preemptible ring3 task.
  • 14: kernel object model + per-process handle tables done — the NT-style piece: a kernel-wide object table plus a per-process handle table, bounds-checked and existence-checked, never trusted as a raw index.
  • 15: IPC channels between isolated processes done — real blocking message-passing, reusing the scheduler's existing blocking mechanism (a second wake condition alongside the existing tick check) instead of inventing a second one.

Phase VI–VII: storage, VFS, real process spawning

  • 16: a legacy ATA PIO disk driver done — the first real storage I/O this kernel has ever done, talking directly to the classic ISA IDE ports. Verified three independent ways, including confirming a write directly in the disk image file from the host afterward.
  • 17: MiniFS, a minimal custom filesystem done — a fixed-layout superblock + a one-sector flat directory + a contiguous per-file data region. Verified formatting, creating two files, and reading each back correctly and distinctly.
  • 18: a VFS abstraction over MiniFS done — a basic namespace (/system, /devices) via a small mount table — the identical read call reaches two completely different mechanisms depending only on the path prefix.
  • 19: real Process.spawn() from disk done — "the shell launches a program" becomes genuinely real, reading a file through the VFS instead of a statically embedded blob. Running two ring3-capable processes at once immediately reproduced a real TSS.RSP0 collision, fixed by giving every ring3 task its own private RSP0 target.

Phase VIII: MiniC methods, the native API, a POSIX shim

  • 20: real method-call syntax in MiniC itself done — a compiler-repo milestone, not a kernel one: <ReturnType> <StructName>.<methodName>(<StructName>* self, ...) declarations. Needed zero parser changes at call sites — every bit of new logic lives in codegen. Pure syntax sugar, not a new dispatch mechanism. See minic's examples/methods_demo.mc.
  • 21: a real compiled-MiniC program running in ring3 done — every ring3 program until now was hand-assembled; the loader's "copy one contiguous byte range, jump to its first byte" model doesn't survive unmodified for compiled output, since string literals and globals land in separate ELF sections. Fixed with a standalone link + objcopy -O binary flattening step, no compiler changes.
  • 22: a real native "File" API with real methods done — the first slice of the native System API. Two new syscalls expose VFS read/write to ring3 for the first time; File.write(...)/File.read(...) are real methods wrapping them — the first time this kernel's method-call syntax got used for something real.
  • 23: real Process/Channel methods done — wraps the other two native-API resources the same way. channelReceive is this kernel's first ever blocking syscall. A ring3 process blocks on an operator-triggered channel and then spawns a second instance of itself once triggered.
  • 24: a thin POSIX-shaped shim done — open/read/write/close, implemented entirely in ring3 MiniC over the existing File API, no new syscalls or kernel changes. Growing the compiled ring3 program past one page for the first time surfaced three real, previously-latent kernel bugs — see the Architecture page.

Phase VIII (milestones 20–24) is complete. See the Architecture page for the technical detail behind each of these, and the Walkthrough for real captured proof.

Phase IX: capabilities & security hardening

  • 25: real per-handle rights on Channel done — Phase IX's first step, closing the exact gap milestone 23/24 flagged: a valid channel handle could be used for any operation the channel supported, with no per-handle ownership. A new Handle.rights bitmask (fixed forever at grant time) and a new OBJ_CHANNEL object type wrap Channel in the handle table for the first time. channelSend/channelReceive now resolve a real handle and check its rights before touching the underlying channel; a new openChannel syscall is the one place an index becomes a handle — and always grants receive-only rights, a real and deliberate policy choice, not a placeholder. Verified in QEMU: a fresh boot's Channel.open() succeeds, an immediate unauthorized Channel.send() through that exact handle is correctly rejected, and the authorized Channel.receive() on the same handle still works normally afterward. See the Architecture page and the Walkthrough for the real rejected-send proof.
  • 26: security hardening on the shared PDPT region done — Phase IX's second step, closing the shared-region gap flagged since milestone 12. Tracing every actual leaf-level mapPage/mapPageIn call site first showed the real, exploitable surface was narrower than assumed — the heap and the map demo already used leaf flags without the user bit, so the true gap was specifically boot.s's static identity map's 2MB huge-page leaves (PDPT index 0). cloneAddressSpace() now strips the user bit from its copy of the kernel's PDPT[0]/PDPT[1] entries when building a new (ring3-capable) address space — the original kernel address space and boot.s itself are untouched, since nothing runs those in ring3 anyway, and every legitimate ring3 interaction with this region already goes through a syscall regardless. Verified with a genuine negative-space proof: a new shell command, ring3fault, sends a deliberate forbidden-write trigger, and the boot-time ring3 process's attempted write to the kernel's own load address (0x100000) takes a real page fault — the existing handler reports the exact faulting address and halts, and the "it worked" line the test was written to catch never prints. A full regression pass confirmed nothing legitimate broke. See the Architecture page and the Walkthrough for the real captured fault.
  • Next: extending real per-handle rights to Process handles too, or further security hardening (NX/ASLR/sandboxing).

What's next after Phase IX

  • Phase X — a real driver framework (PCI enumeration) + networking (NIC driver, a from-scratch TCP/IP stack) — deliberately last: the largest remaining subsystem, with the fewest things depending on it.
  • Phase XI — service architecture + a real init — the current hardcoded shell loop migrates to an actual userspace program once processes/IPC/VFS exist to support that; async I/O as a cross-cutting pass once sync I/O works everywhere.

Self-hosting (minicc, compiled for MiniC OS's own target, running on MiniC OS to compile something) isn't one of these phases — it's an ongoing checkpoint tried after each major phase, with the real prerequisites (native API, real file I/O, real process spawning) already in place as of Phase VIII.
