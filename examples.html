The boot-time ring3 process

Before the shell even shows its first prompt, a real gcc-compiled program (not hand-assembled) has already been loaded into its own isolated address space and started running in ring 3, preemptible by the timer like any other task. The two hello from a LOADED process! lines are printed from inside that loaded, executing code via a real int 0x80 syscall — a message that lives inside the loaded blob itself, not a kernel string.

handle 0 (self) -> task_index 0x7 is the process resolving its own well-known handle all the way through the kernel object table to real ground truth — 0x7 is exactly what ps independently reports for this same process later, meaning two completely different code paths (a ring3 syscall's handle lookup, and the shell's direct table read) land on the identical number. handle 99 (invalid) — never allocated — comes back as the same -1 sentinel every failure path uses, not garbage or a crash.

The File.write()/File.read() and POSIX lines are the native API and the POSIX shim, both exercised from inside that same ring3 process — real C function calls (file_write(&msg_file, ...), a plain function taking an explicit self pointer) and real free-function calls (write(fd, ...)) wrapping two different syscalls, not raw syscall numbers either way. The two separate POSIX read() lines return two different, correct slices of the same underlying buffer — proof the position cursor genuinely advances between calls, not just replaying the whole buffer each time.

Channel.open() ok=0x1 and unauthorized Channel.send() succeeded=0x0 are the real capability/rights proof. open() turns a raw channel index into a real handle — but the kernel's own policy only ever grants that handle receive rights, never send rights. The very next line deliberately attempts to send through that exact handle anyway — and succeeded=0x0 (false) is the actual point: without real per-handle rights enforcement, checked before the underlying channel is ever touched, this call would have silently succeeded. The receive that follows later in the session, through that same handle, still works normally — the restriction is real but not overzealous.

Heap & frames

Two allocs land exactly where hand arithmetic predicts; free then mem shows the byte given back matches exactly. frames' count is built entirely from parsing the real multiboot memory map at boot — not a made-up number.

Paging

map proves the whole dynamic-paging chain end to end: a physical frame beyond the multiboot memory map's low end, mapped at a virtual address a full 1GB past anything the boot-time static map set up, written through and read back correctly — real PML4/PDPT/PD/PT walking and on-demand table creation, not just "an address came back."

Scheduler

tasks proves both preemption and blocking in one line. Two purely cooperative tasks stay in exact lockstep. A third — a tight loop that never calls yield() at all — runs six orders of magnitude ahead, because it spins its entire timer slice every turn instead of giving up the CPU voluntarily; only possible if the timer genuinely forces control away from it periodically. A fourth, sleeping between increments, tracks ticks / interval almost exactly — proof sleep() really removes a task from the round-robin for that long, not a no-op.

Process isolation

procs: two tasks map the identical virtual address in their own private address space to their own physical frame, and each keeps reading back its own distinct constant forever. The @phys addresses being genuinely different is the real proof — not just "two different numbers came back," but that the same virtual address resolves to two different physical frames depending on which address space is asking, exactly what isolation has to mean.

IPC

The first two chan reads, with an arbitrary number of other commands run in between, show a receiver task genuinely still blocked on an empty channel — not a short timeout, not a no-op. send calls the kernel-side channel_send() directly from the shell's own context; the instant it succeeds, the next chan shows the exact value, and the receiver (an isolated process with its own private address space) woke up on its own. The message genuinely crossed from one isolated address space to another through the channel, not shared memory.

PCI bus enumeration

pci's strength comes from being checkable against something this kernel had no part in choosing: QEMU's own default machine model. Every vendor:device pair reported is a real, publicly documented ID — 0x8086:0x1237 (the i440FX host bridge), 0x8086:0x7000/0x7010/0x7113 (PIIX3 ISA bridge, IDE controller, and PIIX4 ACPI bridge — 0x7010 is literally the same IDE controller disk/diskwrite below already talk to, just now independently discovered instead of assumed), 0x1234:0x1111 (the Bochs/QEMU standard VGA device), and 0x8086:0x100e — a real Intel e1000 gigabit NIC, found with zero extra QEMU flags and the target device for the next Phase X milestone. Getting a wrong answer here (a garbage vendor ID, a missing or extra device) would be immediately checkable against public PCI ID databases — the same "a wrong answer is obviously wrong" property every milestone's verification here has looked for since milestone 1.

A real e1000 NIC driver

nic is milestone 30's proof, and its strength is the same shape as pci's: checkable against a value this kernel had no part in producing. 52:54:00:12:34:56 is QEMU's own well-known, publicly documented default NIC MAC address — reading it back correctly means net/e1000.c genuinely enabled the device over PCI, correctly found and mapped its real physical MMIO register file (not RAM — the first device-register mapping this kernel has ever done), and pulled real hardware state out of it (RAL0/RAH0, pre-loaded by QEMU's own emulated EEPROM). A broken mapping, a wrong BAR, or garbage register reads would have produced a zeroed or nonsense MAC instead — immediately, independently wrong, not just "the command didn't crash." link_up=0x1 is a second, separate piece of real hardware state confirming the same thing. No packet has been sent or received yet — this milestone proves the driver can talk to the hardware, deliberately not more than that.

A real ARP resolver

arp is milestone 32's proof, exercising the real net/arp.c resolver instead of milestone 31's own hardcoded one-shot flow — four separate, independently checkable claims in one command. resolve gateway ok=0x1 mac=52:55:0a:00:02:02 is a genuine external round trip, the same shape milestone 31 first proved, now through the real API: QEMU's SLIRP backend, running entirely outside this kernel, received a real ARP request and replied with its own well-known, publicly documented default gateway MAC. elapsed_ticks=0x64 (100 ticks) is real, non-trivial wall-clock time — an actual network round trip took a measurable amount of it.

cached_ok=0x1 cached_elapsed_ticks=0x0 is the real proof of the cache: resolving the identical address a SECOND time returns instantly, zero ticks elapsed, because it never sends a packet at all — a concrete, timing-based behavioral difference between a cache hit and a cache miss, not just "the second call returned the same answer as the first" (which a broken cache that silently re-resolved every time would also produce). resolve_dns_proxy_ok=0x1 dns_mac=52:55:0a:00:02:03 resolves a second, different real address — QEMU SLIRP's own built-in DNS proxy — and gets back a genuinely different MAC that follows the exact same publicly documented SLIRP convention (embedding the IP's last three octets), proving the resolver generalizes past the one fixed address milestone 31 ever exercised.

resolve_unreachable_ok=0x0 is the negative-space proof: asking to resolve an address nothing ever answers for (10.0.2.99) correctly returns false once the resolver's own real tick-bounded timeout expires, rather than hanging forever or returning garbage — a real, honest failure result for a real failure case.

A real IP layer

ping is milestone 33's proof — a genuine ICMP echo round trip through the full stack built so far: ARP resolution, real IPv4 header construction, a real checksum, and a real Ethernet send/ receive, all in one command. ok=0x1 means net/icmp.c's icmp_ping() got back a reply that matched on every real, independently meaningful field — the right EtherType, the right IP protocol number, the right source IP, the right ICMP type (echo reply, not some other ICMP message), and the exact identifier/sequence number this specific request sent — not just "some ICMP traffic arrived."

A wrong IP header (a bad checksum, a malformed field) would most likely have gotten the packet silently dropped by QEMU's real host-level network stack rather than answered at all, so the reply arriving at all is itself strong indirect evidence the header was built correctly — the same "external validation beats self-validation" property every proof in this networking phase has looked for. elapsed_ticks=0x64 matches the same real, non-trivial round-trip time arp measured moments earlier — consistent, not coincidental, real network latency.

This is also the first milestone in this whole project to give the kernel a real, explicit "my IP address" (net/ip.c's g_my_ip) — previously a bare literal duplicated inside arp.c's own request-building code, now one shared, named value both files use.

A real UDP layer

dns is milestone 34's proof — a real UDP datagram, correctly checksummed against its own pseudo-header, carrying a genuine DNS query to QEMU SLIRP's built-in resolver proxy (10.0.2.3, the same address arp already resolved back in milestone 32). ok=0x1 means net/dns.c's dns_query() got back a response matching the exact transaction ID this query sent, with the response (QR) bit set, and at least one real answer record — meaning SLIRP's proxy genuinely forwarded the query to a real upstream resolver and got a real answer back, not something this kernel could produce on its own.

elapsed_ticks=0x74 (116 ticks) is itself a meaningful detail worth noticing: noticeably higher than ping's own elapsed_ticks=0x64 — real, consistent with DNS resolution genuinely taking one more hop than ICMP echo (SLIRP forwards the query out to a real resolver and waits for its reply, rather than answering directly the way it does for ping) — exactly the kind of small, correct-shaped detail that would be hard to fake by accident.

Disk & filesystem

disk reads back an exact signature written from the host side before the kernel ever booted — real reads against independently-verifiable content. diskwrite writes a distinct 256-value repeating byte pattern and reads it straight back, reporting a byte-exact match — proves the write path independently of the read path. mkfs/mkfile/cat creates two files back to back and reads each one back correctly and distinctly, even after the other exists — no cross-file clobbering, and reads are always fresh from disk, never a cached copy.

VFS

vfscat /system/file0.mfs and vfscat /devices/ticks back to back is the actual point of the VFS layer: the identical function call reaches two completely different mechanisms — real disk I/O vs. live kernel state, no disk touched at all — depending only on the path prefix.

Process spawning from disk

install writes the kernel's own compiled-in test program out to a real file (the byte count is the real, host-verifiable size of that compiled-and-flattened blob). spawn reads it back and launches an independent second process — ps afterward shows two real processes with genuinely different cr3 values, confirmed from the kernel's own bookkeeping.

A ring3 process spawning itself

ring3go takes a completely different path from install/spawn above: instead of the shell (kernel mode) launching a process, it wakes the boot-time ring3 process's own blocking Channel.receive() syscall — a real ring3 process blocking itself on a syscall for the first time in this kernel's history. Once it wakes, it calls Process.spawn() itself:

hello from a LOADED process! 0xc0ffee

Everything from the first hello from a LOADED process! onward is the spawned child — the exact same program, running its own _start() from scratch in its own freshly cloned address space, with its own distinct task index (0x9, not the parent's 0x7) and its own independent handle table. As of milestone 27 it's genuinely interleaved with the parent's own remaining code, not simply "runs after" — a real preemptive scheduler doesn't guarantee which one runs first, which is why the child's first print lands before the parent's own Process.spawn() launched... line in this particular capture. What doesn't vary is which values each side reports. The child reaches its own Channel.receive() too, but the single-slot mailbox is already empty again (the parent's own receive() consumed the one message ring3go sent) — so it just blocks there forever, never reaching its own Process.spawn() call. That's what stops this from spawning a second, third, fourth generation automatically: no recursion-guard flag needed, just the mailbox's own single-slot semantics.

ProcessHandle.open(rights=0) ok=0x1 through authorized ProcessHandle.query() got task_index 0x9 are milestone 27's proof, run by the parent right after Process.spawn(), targeting the child it just launched. Requesting zero rights still yields a real, valid handle (ok=0x1) — a handle's existence and its rights are two separate things, same as milestone 25 established for Channel. The next line is the actual point: querying through that rights-less handle is correctly rejected. A second handle, this time requesting RIGHT_QUERY, succeeds — and its query returns 0x9, the exact task_index Process.spawn() already reported two lines earlier, an independent cross-check rather than a hardcoded echo. The handle 0 (self) -> task_index 0x9 line in between is the child's own pre-existing self-query (rights-granted since milestone 14, actually verified for the first time here) — still correct, confirming the newly-real check doesn't break the one path already depending on it.

(The child's own File.write() shows the "already exists" failure sentinel here rather than a fresh byte count — the parent already wrote that same file earlier in this same boot, and MiniFS correctly refuses to overwrite an existing file. File.read() still succeeds, reading back the real, persisted content either way.)

A deliberate forbidden ring3 write

ring3fault is a separate, dedicated session — deliberately not run alongside anything else, since it ends by halting the kernel on purpose. It sends a second trigger value on the same channel ring3go uses, causing the boot-time ring3 process to attempt a forbidden write instead of spawning a child: 

> ring3fault
sent ring3 forbidden-write trigger - expect a page fault
Channel.receive() got trigger 0x2
attempting forbidden ring3 write to 0x100000
page fault at 0x100000, error_code=0x7, halting

This is milestone 26's actual proof. attempting forbidden ring3 write to 0x100000 confirms the process really reached the write attempt; the very next line the source would have printed on success — "forbidden write succeeded (BUG!) at 0x..." — never appears, because the CPU faulted on the write itself before that syscall could even be staged. page fault at 0x100000, error_code=0x7, halting is the kernel's existing page-fault handler independently confirming the exact faulting address (read from CR2, not anything the ring3 process reported about itself) — 0x100000, the kernel's own multiboot load address, inside the shared region every address space carries but never something this process mapped for itself. Before this milestone's fix, the same command printed the "(BUG!)" line and kept running, the write landing silently in live kernel memory — the absence of that line, replaced by a fault at exactly the address written to, is what makes this a real negative-space proof. error_code=0x7 (present + write + user — milestone 28's addition to this handler) confirms it specifically as a write violation, worth comparing directly against the NX proof below.

A deliberate stack-execution attempt

ring3nx is milestone 28's proof — same one-shot, kernel-halting shape as ring3fault, a third trigger value on the same channel. Instead of writing to forbidden kernel memory, the boot-time process writes a real ret opcode (0xC3) onto its own user stack and attempts to execute it: 

> ring3nx
sent ring3 stack-execution trigger - expect a page fault
Channel.receive() got trigger 0x3
attempting to execute ring3 stack byte at 0x80020000
page fault at 0x80020000, error_code=0x15, halting

If PAGE_NX (mm/paging.c) weren't actually enforced on the stack mapping, this would be completely harmless — a bare ret just pops the return address the preceding call pushed and jumps straight back — so the "stack execution succeeded (BUG!)" line right after it in the source would print. It never does. error_code=0x15 (binary 10101: present + user + bit 4, instruction fetch) is the actual proof — the CPU's own hardware signal that this specific access was an execute attempt, not a coincidental fault. Directly comparable against ring3fault's own error_code=0x7 (bit 4 clear) captured moments above: two different deliberate violations, two different, independently-checkable error-code signatures.
