Capabilities

What the kernel currently supports

Every capability below was scoped as one hard problem at a time and proven with a concrete, checkable assertion in QEMU — never just "it didn't crash." The long-term architecture (a UNIX namespace/shell + NT-style kernel objects/handles + microkernel-ish IPC/service isolation + a capability security model, exposed through a native API with a POSIX compatibility layer on top) is real and already substantially built, grouped below by subsystem rather than by the order it was built in. See the Architecture page for the full technical depth behind each of these, and the Walkthrough for real captured QEMU proof.

Boot, memory & scheduling

  • Boots to 64-bit long mode — a multiboot1 image transitions from 32-bit protected mode into real 64-bit long mode and writes to the VGA text buffer directly. The 32-to-64-bit transition is hand-written in boot/boot.s — below what a C function body can express, same as every kernel project; everything past that point is C.
  • Real interrupts — an IDT of real entries, the 8259 PIC remapped, the PIT reconfigured to ~100Hz, working timer + keyboard handlers.
  • A real free-list heap — kalloc splits blocks and kfree coalesces adjacent free ones in both directions, growing a chunk at a time as the free list runs dry rather than a fixed reservation.
  • Real dynamic paging — walks/creates a full PML4→PDPT→PD→PT chain of 4KB pages on demand, backed by a physical frame allocator built from the multiboot memory map, so the kernel can map memory anywhere, not just inside the static identity map.
  • A preemptive scheduler — a hand-written context switch, a fixed table of tasks each with its own stack, the timer interrupt forcing real task switches rather than relying on voluntary cooperation, plus real task blocking via sleep().

Ring 3, process isolation & the kernel object model

  • A real ring0/ring3 privilege boundary — a GDT ring3 code/data pair, a TSS (RSP0 on its own dedicated stack), and an int 0x80 syscall gate (DPL=3) with a real dispatcher. Verified by reading back cs=0x1B from inside ring3 (real CPL 3, not just "a syscall happened").
  • Real per-process address-space isolation — each process gets its own PML4, with a private region no other task can see even at the identical virtual address. Verified: the same virtual address genuinely resolves to two different physical frames depending on which address space is asking.
  • A real process loader — copies a byte range into a freshly cloned private address space and schedules it as a genuinely preemptible ring3 task. A process can be spawned from a VFS file path, from a fixed compile-time-embedded program, or from a program registered at runtime.
  • An NT-style kernel object model — a kernel-wide object table plus a per-process handle table, bounds-checked and existence-checked, never trusted as a raw index. Ring3 code only ever sees a small integer handle.
  • A full process lifecycle with real resource reclamation — a process can exit, and everything tied to it is genuinely freed: its private-region frames and PML4/PDPT, its process/task table slot (reused by the next spawn instead of growing the table forever, including reusing its own already-allocated kernel stack), and its own kernel-object handle table. A process can also release one of its own handles early, without exiting — needed because a handle one process holds to another lives in the holder's table, so only the holder can free it. Verified with exact hand arithmetic: the object table's live count returns to the exact clean-boot baseline after repeated spawn/exit/restart cycles, not just a smaller leak.
  • A real init process with genuine supervision — a dedicated ring3 process spawns a real service, polls it until it exits, and restarts it. Services can be registered at runtime (loaded from a VFS file into a registry slot spawn_builtin can address by index) and unregistered again for genuine slot reuse, alongside the one fixed compile-time entry.

Capabilities & security hardening

  • Real per-handle rights on both Channel and Process — a handle's rights are fixed forever at grant time and checked before the underlying object is ever touched. A handle granted receive-only genuinely cannot be used to send, verified with a real rejected send attempt.
  • The shared kernel/heap region is protected from ring3 — a cloned (ring3-capable) address space's copy of the shared PDPT entries has the user bit stripped, verified with a real forbidden-write page fault. Every legitimate ring3 interaction with this region goes through a syscall instead.
  • Real NX (no-execute) enforcement on every dynamically-mapped pure-data region, including every ring3 process's own user stack — verified with a real page fault carrying the CPU's own instruction-fetch bit, distinct from a plain write-violation fault.
  • Cross-process capabilities — one process can open a handle to another process with a requested rights set, and gets back only the intersection of what it asked for and what's actually grantable.

IPC, storage & the native API

  • Real blocking IPC channels between isolated processes — reuses the scheduler's existing blocking mechanism (a second wake condition alongside the existing tick check) instead of inventing a second one.
  • A legacy ATA PIO disk driver — real sector read/write talking directly to the classic ISA IDE ports.
  • MiniFS, a minimal custom filesystem — a fixed-layout superblock, a flat directory, and a contiguous per-file data region.
  • A VFS abstraction — a basic namespace (/system, /devices) via a small mount table, where the identical read call reaches two completely different mechanisms depending only on the path prefix.
  • A native File/Channel/Process API with real methods, plus a thin POSIX-shaped shim (open/read/write/close) implemented entirely in ring3 C over the existing File API, no extra syscalls needed.
  • Compiled C running in ring 3 — ring3 processes are real, gcc-compiled programs, not hand-assembled blobs, using this kernel's own native API.
  • Genuinely asynchronous file reads — a process issues a read and gets back a handle immediately, does other real work of its own choosing, then collects the result only when it actually needs it. A dedicated kernel worker task performs the real disk read concurrently (cooperative multitasking standing in for real DMA/interrupts, since the ATA driver is PIO-only), and the caller only blocks - via the same scheduler wake-condition mechanism blocking IPC receive already uses - once it asks to wait for a result that isn't ready. Verified: several real prints from the calling process land between issuing the read and waiting for it, proving it wasn't stalled, and the async result's byte count and content exactly match an earlier synchronous read of the same file.

Hardware discovery & networking

  • PCI bus enumeration — walks the legacy CONFIG_ADDRESS/CONFIG_DATA mechanism to discover real hardware instead of trusting a hardcoded I/O port, verified against QEMU's own default machine model's real, publicly documented vendor:device IDs.
  • A real e1000 NIC driver — enables the device over PCI, maps its memory-mapped register file, and moves real packets through real TX/RX descriptor rings.
  • A real ARP resolver with a genuine cache — a second resolve of the same address returns instantly (checkable by real elapsed ticks), and the resolver generalizes to any target address, not just one fixed one.
  • A real IPv4 layer, verified with a genuine ICMP echo (ping) round trip through the full stack: ARP resolution, real header construction, a real checksum, and a real Ethernet send/receive.
  • A real UDP layer, verified with a genuine DNS query answered by a real upstream resolver through QEMU's own network backend — not a loopback, not self-validation.
  • A real TCP client, verified with a genuine HTTP GET to a real internet host: a real 3-way handshake, a real data segment, a receive loop that ACKs each arriving segment, and a best-effort graceful close. The one distinction no earlier protocol layer needed: a real internet host doesn't answer ARP from this guest, so the gateway's MAC is resolved for the Ethernet-level destination while the real remote IP goes in the IP header — routing, not resolution, deciding an off-subnet frame's link-layer destination.

Language history

This kernel was originally built in MiniC, a small hand-rolled systems language with its own compiler, no LLVM. Once day-to-day development speed became the priority, MiniC and its compiler were retired and the kernel was rewritten by hand into freestanding C — every source file independently re-verified in QEMU against its own already-known-good behavior before the MiniC original was deleted, not a bulk mechanical translation trusted on faith. One real, C-specific bug was found and fixed during the rewrite: spawn_process()'s "jump to byte 0 of the loaded image" loader assumed the entry function always lands first — true for MiniC's own single-pass codegen, but not for gcc, which laid out the ring3 program's functions in a different order — fixed with a dedicated linker section pinning _start to offset 0 regardless of source order. Everything else carried over unchanged in behavior: same architecture, same verification bar, same "no external libraries" rule — only the implementation language changed. See the kernel repo's own README and git history for the full writeup, one commit per rewrite stage.

What's still ahead

The existing hardcoded shell loop migrating to a real userspace program is explicitly not the next step — most of its command surface touches raw kernel internals that shouldn't be arbitrary userspace syscalls in a real design, a substantially bigger and separate problem from the process/service architecture above. Async file reads exist now, but async I/O as a genuinely cross-cutting pass doesn't yet - network operations (ARP/ICMP/UDP/ TCP) are all still fully synchronous, busy-polling with no way for a process to do anything else while one is in flight. The narrower gaps are documented on the Known limitations section of the Architecture page.

Self-hosting used to be framed as "the compiler compiled for this kernel's own target, running on this kernel to compile something" — that goal doesn't carry over as-is now that MiniC itself is retired (see Language history above); getting a real C toolchain running natively on this kernel is a substantially bigger undertaking than porting one small hand-rolled compiler was, and isn't a near-term goal. The real prerequisites this kernel already has either way (native API, real file I/O, real process spawning) mean the door isn't closed — just not something to plan around until much later.
