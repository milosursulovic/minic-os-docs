Architecture

How MiniC OS is built

Almost everything past the boot transition is ordinary, hand-written freestanding C. The only hand-written x86 assembly is what's genuinely below what a C function body (even real GCC inline asm, which has real operand binding) can express: program structure, not logic — the 32-to-64-bit boot transition, interrupt entry stubs, and context switching.

Milestones 1 through 34 (everything through the networking phase) were built in MiniC, a small hand-rolled language with its own compiler. Right after milestone 34 shipped, the whole kernel was rewritten by hand into freestanding C for faster day-to-day development — the architecture, milestones, and verification bar didn't change, only the implementation language did. See the Roadmap for that rewrite as a real, dated entry. This page describes the kernel's current C implementation throughout.

Boot process

Multiboot1 drops the kernel in 32-bit protected mode; this kernel runs in 64-bit long mode. Getting from one to the other — loading a GDT, building page tables, enabling long mode, far-jumping into a 64-bit code segment — is hand-written in boot/boot.s, the same way every kernel project does it, even ones written in Rust or Zig. boot/linker.ld places the multiboot header and code at the conventional 1MB load address multiboot expects.

QEMU's multiboot1 -kernel loader hard-rejects a genuine ELF64 image ("Cannot load x86-64 image, give a 32bit one"), so every object — hand-written .s and gcc-compiled .c alike — still links as ld -m elf_i386 even though the code inside runs in real 64-bit long mode: each .c file compiles to assembly, gets a literal .code64 directive prepended, and is fed to as --32, which encodes the 64-bit mnemonics correctly while keeping the ELF32 container format. Two gcc flags this pipeline specifically needs: -fPIC (otherwise a global's absolute 64-bit address needs a relocation type unrepresentable in an ELF32 table) and -fvisibility=hidden (otherwise a reference to an external symbol routes through the GOT via an ELF64-only relocation syntax as --32 can't parse — every header wraps its declarations in #pragma GCC visibility push(hidden)/pop).

boot.s also owns the GDT/TSS setup: a ring3 code/data segment pair alongside the ring0 ones, and a TSS whose RSP0 field tells the CPU which stack to switch to on any ring3→ring0 transition. RSP0 is an absolute reset point, not a continuation — the CPU loads it fresh on every transition, so pointing it at a stack something else is still using silently corrupts that other thing's state. boot.s sets it once, to its own dedicated stack, as a safe initial value; from the process model onward (see below), the scheduler repoints it per-task on every context switch instead.

Once in 64-bit mode, boot.s calls the kernel's own entry point, _start() in kmain.c — everything past that point is ordinary freestanding C: volatile, packed struct, pointer arithmetic, and real GCC inline asm for the handful of raw instructions C has no other way to express: out/in/lidt/sti/ invlpg, reading cr2/cr3.

Memory map

RegionWhat's there
0 – 1GBthe boot-time static identity map (boot.s's own page tables) — kernel code, stack, heap, and every demo command's memory all live here, shared and mapped identically in every address space (PDPT[0]/PDPT[1])
0x80000000+ (PDPT[2] and up)each process's private region — not present by default in a freshly cloned address space, populated on demand only by whichever task owns that PML4. This is where a loaded ring3 process's own code/data (0x80000000) and user stack (0x80020000) live.
As of milestone 26, a cloned (ring3-capable) address space's copy of PDPT[0]/PDPT[1] has the user bit stripped — a ring3 process can no longer read/write/execute this region directly, only through a syscall (which raises CPL to 0 first). See Memory protection below.

Scheduler

A fixed table of tasks, each with its own kalloc'd stack. create_task() hand-builds a new task's initial stack to look exactly like what the hand-written switch_context() would have left behind, with the task's entry point as a fake "return address" — the first switch into a never-run task lands there via an ordinary ret, no special-casing needed for "first run" vs "resuming."

yield() round-robins to the next non-blocked task — called voluntarily by cooperative tasks, and also called from inside the timer interrupt handler, which is what makes scheduling preemptive: since the interrupt handler is just an ordinary nested C call on whichever task's stack the CPU happened to interrupt, calling yield() from inside it suspends that call exactly like a voluntary yield() would.

sleep(ticks) adds real blocking: a task marks itself blocked with a wake tick and yields away; the scan skips blocked tasks, waking one up the moment its condition is met. Channel receive (see IPC below) reuses this exact mechanism with a second kind of wake condition, not a separate blocking primitive.

Process model & isolation

Real per-process address-space isolation: clone_address_space() builds a fresh PML4 whose entry 0 points at a fresh PDPT that shares PDPT[0]/PDPT[1] (identity map + heap) with the kernel's own PDPT — literally the same physical sub-tables, so kernel code/stack/heap stay reachable unchanged — while everything from PDPT[2] up starts out not-present, private to whichever task gets that PML4.

spawn_process(image_start, image_end, load_vaddr, stack_vaddr) is the real loader: clones a fresh address space, maps and copies a byte range into it page by page, maps a user stack, then creates a scheduler task whose kernel-mode entry does exactly one thing — enter ring3 at the loaded address via a hand-written fake-iretq-frame trick. From then on the task only ever runs in ring3, preemptible by the timer like any other task. spawn_process_from_path(path, ...) is the same loader fed from a real file read through the VFS instead of a pointer range.

A kernel-wide kernel_object table plus a separate per-process handle table give ring3 code a small integer instead of a raw kernel pointer — resolve_handle(process_index, handle) is the one place that integer becomes a real object index, bounds- checked and existence-checked, never trusted directly. Every process gets a handle to itself for free, guaranteed to land in the well-known slot 0 (a fresh handle table starts empty, so the first allocation into it always takes slot 0).

Milestone 36 adds a third way to spawn a process alongside the two above: spawn_builtin (syscall 11) lets a ring3 process spawn another ring3 process from a small, fixed, kernel-embedded program registry, addressed by index rather than a raw pointer or a filesystem path. This is what proc/init.c — the kernel's first real init process, spawned by kmain.c at boot the same way the existing demo process always has been — uses to launch proc/hello_service.c without needing the filesystem to have anything on it yet (a fresh disk.img is empty until mkfs+install run manually). The registry is intentionally not a raw-pointer API: letting ring3 code name an arbitrary address as "a program to run" would undo the real work the capability/rights phase (milestones 25-27) put into making sure ring3 code can only ever act through something the kernel already vetted.

Milestone 37 adds the other half of a process's real lifecycle: process_exit (syscall 12) lets the calling task mark its own task and process table slots as no-longer-alive, then yield away for the last time. sched/task.c's scheduler scan permanently skips a slot marked this way — the exact same shape it already uses to skip a temporarily blocked task, just with no wake condition that will ever fire. task.used/process.used turned out to already exist as fields but be entirely write-only (set true at creation, never read anywhere) before this milestone — giving them their first real meaning needed no new fields at all. Deliberately does not reclaim the exited process's resources: its frames stay mapped, its table slot stays occupied forever, and any handle still pointing at it stays valid but now points at something that will never run again — real, separate follow-on work, not an oversight. proc/hello_service.c now calls process_exit() right after its own startup message instead of idling forever, and the ps shell command gained an exited=0x field per process so this is directly observable — a fresh boot shows the boot-time demo and init both exited=0x0 while hello_service alone shows exited=0x1, immediately and every time.

Milestone 38 closes the loop: init.c now opens a ProcessHandle to its spawned service and busy-polls its query (syscall 3) until it fails, then spawns a fresh instance - real restart-on-exit, not just spawn-and-forget. That needed a real fix: syscall 3 previously resolved an OBJ_PROCESS handle straight to a task_index with no check on whether the target had actually exited, so querying a handle to an already-dead process silently returned a stale task_index instead of failing - fixed with a one-line check against g_processes[proc_idx].used. Deliberately restarts only once: the process table is a fixed 4 slots, already full after the demo, init, and two hello_service instances, and there's still no resource reclamation on exit for a real looping supervisor to rely on. No yield/sleep syscall exists for ring3 yet, so the poll busy-spins - acceptable here since hello_service exits almost immediately.

Milestone 39 gives process_exit real teeth: a new mm/paging.c function, free_address_space(pml4_phys), walks the exiting process's own page tables (PDPT[2..511] -> PD -> PT - the private per-process region; PDPT[0]/ [1], the shared kernel/heap sub-tables, are never touched), freeing every present leaf frame plus the PT/PD frames themselves, then the process's own PDPT and PML4 frames. Safe to call from inside process_exit() even though it tears down the caller's own address space: the syscall runs in kernel mode on the shared identity map throughout, and CR3 only actually moves off the freed PML4 once yield()'s own load_cr3() runs immediately after. Still not reclaimed: the process/task table slot itself, and the task's own kalloc'd kernel stack (freeing your own currently-executing stack from within itself is a genuinely riskier problem than freeing memory you're not standing on). Verified with real diagnostic prints of g_free_frame_count around the free (added, used to get exact numbers, then removed): both of hello_service's exit cycles returned the free count to the identical baseline, and ps showed the second spawn's cr3 was bit-for-bit the same physical frame the first spawn's exit had just freed - real reuse, not coincidence.

Milestone 40 closes the remaining gap: spawn_process() and create_task_with_cr3() now search for an exited slot before appending, so the process/task table no longer only ever grows. create_task_with_cr3() changed from bool to int (the real task index, or -1) - a reused slot's index can't be inferred as "whatever the counter currently is" the way an always-appended one could. That surfaced two real, previously-latent bugs: a pre-computed task_index = g_task_count in process.c would have used the wrong index once reuse landed, and create_isolated_task()'s bare return create_task_with_cr3(...) implicitly converted -1 (failure) to true (nonzero is truthy) - silently reporting success on failure. Both fixed by using the real returned index. A reused task slot reuses its old kalloc'd kernel stack directly rather than allocating a fresh one - just reinitializes the fake switch-frame at the top of the same block - sidestepping "freeing your own currently-executing stack from within itself" entirely instead of solving it, and meaning reuse doesn't leak heap memory either. spawn_process() also clears the reused slot's handle table first, since a stale "handle 0" from the previous occupant would otherwise break the "handle 0 = myself" convention for the new one.

A real regression was found and fixed during this milestone's own testing, never shipped: an early version had init restart hello_service 2-3 times in a loop for a more dramatic reuse proof, but each restart also costs a g_objects[8] slot for the query handle - looping that aggressively exhausted the shared, still-unreclaimed object table and broke the original boot-time demo process's own unrelated Channel.open() call, cascading into several other spurious failures downstream. Reverted to a single restart, which already proves reuse cleanly (the same task_index comes back every time) without touching that shared budget any harder than milestone 38 already did.

Milestone 41 fixes that regression at the root instead of just scoping the demo back: process_exit now walks the exiting process's own handle table and frees every object it referenced, via two new functions in proc/object.c, free_object()/free_handle(). alloc_object()/alloc_handle() already scanned for a free slot before appending — they simply never had anything freed to find until this milestone. This also makes spawn_process()'s own milestone-40 handle-table-clearing loop for a reused slot redundant, since the previous occupant's exit now leaves the table clean already; that loop is removed. The scope is deliberately narrow: a handle another process holds to the exiting one — init's own permanent open_process handle onto hello_service, for instance — lives in that other process's own table, not the exiting process's, so exit doesn't touch it. There is also still no handle_close-style syscall, so a process that opens handles to others but never exits itself has no way to release them early — a real, separate gap this milestone doesn't attempt. Verified in QEMU: objs reports 0x4 after a full spawn/exit/restart/exit cycle, matching hand arithmetic exactly (3 boot-time objects plus 1 permanent init-owned object), and re-running the exact scenario that broke during milestone 40's own testing — install+spawn alongside the hello_service restart cycle — now shows Channel.open() ok=0x1 restored, confirming the fix, not just a narrower test.

Milestone 42 closes the narrower gap milestone 41 documented as still open: a handle one process holds to another lives in the holder's own table, not the target's, so the target's own exit never frees it — only the holder explicitly releasing it, or the holder itself exiting, can. New syscall 13, handle_close, validates the handle belongs to the caller and is currently in use, then calls the same free_object()/free_handle() pair milestone 41 already added — no new reclaim mechanism, just a second entry point into it that doesn't require exiting first. init.c now closes its query handle onto hello_service after each restart cycle and loops the restart 3 times instead of once — deliberately reproducing the exact aggressive-restart scenario that exhausted g_objects[8] during milestone 40's own testing, before any reclaim existed. Verified in QEMU, twice: objs reports 0x3 after all 3 restart rounds complete — bit-for-bit the clean-boot baseline, proving 3 full rounds of open/query/close/restart leave zero net object growth rather than just a smaller leak.

Milestone 43 closes the other item flagged as open after milestone 42: spawn_builtin's registry has been fixed at compile time since milestone 36, so a ring3 process could never make a new program spawnable without a kernel rebuild — only spawn one already baked in, or read one from a VFS path directly via spawn_process_from_path (syscall 6), which bypasses the registry's index-based capability model entirely. New syscall 14, register_service, reads a VFS file into one of 4 fixed 16KB runtime registry slots and returns an index. builtin_program_bounds() — already the one function spawn_builtin consults, by index, never a raw pointer — now checks those runtime slots after the one fixed compile-time entry: index 0 stays reserved for hello_service, indices 1+ map to registered slots. spawn_builtin itself needed no changes at all — extending what builtin_program_bounds() recognizes was the entire feature. The boot-time demo process now exercises this on a fourth channel trigger: it registers its own just-installed /system/testprog.bin at runtime, then spawn_builtins it, deliberately taking the new index-based path instead of the already-proven VFS-path one. Verified in QEMU, twice: register_service() returns index 0x1 (the first dynamic slot) both times, and the resulting process's own self-query independently reports the exact same task_index spawn_builtin returned — not an unverified echo — running its full File/POSIX/Channel self-test sequence exactly like any other loaded instance. Deliberately narrow: there's no unregister_service, so the 4 registry slots are a lifetime cap per boot, not a reclaimable resource the way every other table this kernel now reuses is.

Milestone 44 closes that gap: new syscall 15, unregister_service, validates the index maps to a currently-used runtime slot, then clears its used flag and length — the same shape as milestone 41's free_object()/ free_handle(), just for this table. Deliberately doesn't track which process registered a slot, so any process can unregister any slot — matches this kernel's existing pointer- ownership gap (see Known limitations) rather than closing it, real separate work. Unregistering doesn't affect a process already spawned from that slot: spawn_process() copies the image into the new process's own address space at spawn time, so nothing keeps referencing the registry slot afterward. Verified in QEMU, twice: register_service() returns 0x1, unregister_service on it succeeds (0x0), a spawn_builtin(0x1) attempt right after correctly fails (-1) confirming the slot is genuinely freed rather than just marked, registering again returns the same index 0x1 — real reuse, not a second slot — and spawn_builtining that reused index launches a real process whose own self-query matches. objs still reads 0x5, identical to milestone 43's own baseline, confirming the register/unregister/re-register cycle doesn't touch the unrelated kernel object table.

IPC (channels)

A channel is a single-slot mailbox (one u64 message). channel_send() is non-blocking — fails outright if the mailbox is already full, rather than overwriting an unread message or blocking the sender too (a real, separate hard problem, not tackled yet). channel_receive() is the one genuinely new scheduler mechanism: it blocks the calling task exactly the way sleep() already does, just with a channel index set instead of a wake tick — the blocked-task scan gained a second wake condition (a message arriving) alongside the tick check.

The ring0/ring3 boundary & syscall ABI

The calling convention is this kernel's own, since it goes through a software int 0x80 gate rather than the fixed SYSCALL/SYSRET convention: rax = syscall number in / return value out, rdi/rsi/ rdx = up to three arguments.

Capabilities & rights

Every handle carries a rights bitmask, set once when the handle is granted and never widened afterward: 

const int RIGHT_QUERY = 1;
const int RIGHT_SEND = 2;
const int RIGHT_RECEIVE = 4;

open_channel (syscall 9) is the one place a ring3 process can turn a raw channel index into a handle — and the one place the kernel decides policy: it always grants RIGHT_RECEIVE only, regardless of what the caller might want, since nothing in this kernel today needs a ring3-initiated send (the shell always sends directly, in kernel mode). channel_send/ channel_receive check the calling handle's rights before ever touching the underlying channel — a handle obtained through open_channel genuinely cannot be used to send, not just "isn't expected to." See the Walkthrough for a real rejected send attempt.

Milestone 27 extended real enforcement to process handles too. RIGHT_QUERY had existed since milestone 25 and was already granted to every process's own self-handle (since milestone 14) — but syscall 3 never actually checked it, resolving any valid OBJ_PROCESS handle regardless of rights. Now it does, using the same inline check syscalls 7/8/9 use. open_process (syscall 10) is the first real cross-process capability — given another task's index, it mints a handle to that process in the caller's own table, granting the intersection of a caller-requested rights bitmask and what's actually grantable. Requesting 0 still returns a real, valid handle — just one that can do nothing, which is what the negative-space proof actually exercises: a handle opened with no rights genuinely fails to query, while a second handle to the same process opened with RIGHT_QUERY succeeds and reports the correct task_index. See the Walkthrough for the real captured proof.

Memory protection: the shared region, and NX

Milestone 26 closed a real gap: clone_address_space() (mm/paging.c) used to copy the kernel's own PDPT[0]/PDPT[1] entries into every new address space unchanged, including the user (0x04) bit — since x86 paging ANDs that bit across every level from PML4 down to the leaf, a supervisor-only leaf mapping underneath didn't matter if an intermediate PDPT entry above it was user-accessible. Tracing every actual leaf-level map_page/map_page_in call site first showed the real, exploitable surface was narrower than it looked — the heap and the map demo command already passed leaf flags without the user bit, so the actual gap was specifically boot.s's static 1GB identity map's 2MB huge-page leaves (PDPT index 0).

The fix strips the user bit from the copy clone_address_space() makes — boot.s's own tables and the kernel's original address space (g_pml4_phys, used directly by plain kernel tasks that never enter ring3) are untouched. Every legitimate ring3 interaction with this region already goes through a syscall, which raises CPL to 0 before touching kernel memory or the heap — nothing in this kernel needed direct ring3 access to begin with.

Verified with a genuine negative-space proof, not just a topology change: the shell's ring3fault command sends a second trigger value on the existing ring3-demo channel, causing the boot-time process to deliberately attempt a forbidden write to 0x100000 (the kernel's own multiboot load address — present, and never mapped by that process itself). The existing page-fault handler reports the exact faulting address and halts, before the process's own "it worked" print can ever run. See the Walkthrough for the real captured output.

Milestone 28 added real NX (no-execute) enforcement — the classic W^X hardening that stops injected "shellcode" from being jumped to and run. boot.s sets EFER.NXE (bit 11) at boot, in the same rdmsr/ wrmsr round trip as the existing EFER.LME — order matters, since setting a page table entry's NX bit (PTE bit 63) before NXE is live is a reserved-bit violation on every access to that page, not an execute-only restriction. Unlike the "user" bit above (which the CPU ANDs across every translation level, so an intermediate PDPT entry had to be fixed), the CPU ORs the NX bit across every level — only the final leaf PT entry ever needs it set, no intermediate-table change required. Applied to every dynamically-mapped region that's genuinely pure data: the heap, the map demo, the scheduler's private demo mapping, and — the real point — every ring3 process's own user stack. Deliberately not applied to a loaded ring3 program's own code+data image: the loader still flattens a whole compiled program into one contiguous blob with no tracked code/data boundary (see Compiled C in ring 3), so a real W^X split within a loaded image remains open — see Known limitations.

Verified with a real negative-space proof again: the shell's ring3nx command has the boot-time process write a real ret opcode (0xC3) onto its own stack and attempt to call it. The page fault's error code — 0x15 — has the CPU's own instruction-fetch bit (bit 4) set, independently distinguishing this from ring3fault's own write-violation error code (0x7). See the Walkthrough for the real captured output.

The native API

Ring3 processes are real, gcc-compiled C programs (see below), and the native API is a plain C function taking an explicit self pointer wrapping the syscalls above — not raw syscall numbers, and not method-call syntax (that was a MiniC-era feature; self.method(args) becomes type_method(&self, args) in C).

file — whole-file, path-based (no open/close/seek at the kernel level)
typedef struct { char* path; } file;

u64 file_write(file* self, char* buf, u64 len);
u64 file_read(file* self, char* buf, u64 max_len);
channel
typedef struct { int handle; } channel;

bool channel_open(channel* self, int channel_index);   // grants RIGHT_RECEIVE only
bool channel_send(channel* self, u64 value);           // fails without RIGHT_SEND
u64  channel_receive(channel* self);   // blocks; fails without RIGHT_RECEIVE
process — path-based, spawn only
typedef struct { char* path; } process;

u64 process_spawn(process* self, u64 load_vaddr, u64 stack_vaddr);
// returns the new process's task index, or -1
process_handle — handle-based, query an already-running task (milestone 27)
typedef struct { int handle; } process_handle;

bool process_handle_open(process_handle* self, int task_index, int requested_rights);
// grants requested_rights & RIGHT_QUERY - the only right that's ever grantable
u64  process_handle_query(process_handle* self);
// fails without RIGHT_QUERY; else returns the target's real task_index

The POSIX-shaped shim

open/read/write/close — plain free functions, deliberately not methods, matching POSIX's real API shape rather than extending the native OO-style one. Implemented entirely in ring3 C, with no new syscalls and no kernel changes: since file is whole-file only, open() loads (or starts) a per-fd in-memory buffer once, read()/write() serve out of it while advancing a position cursor, and close() flushes a written buffer through file.write() in one shot. 

int open(char* path, int mode);   // 0 = read, 1 = write (create)
int read(int fd, char* buf, int len);
int write(int fd, char* buf, int len);
int close(int fd);
A real, small gap from true POSIX: only one open-for-write "session" can safely target a given path at a time — there's no kernel-side file-descriptor concept backing this, just a per-process in-memory table.

Compiled C in ring 3

Ring3 programs are real, gcc-compiled C — not hand-assembled machine code (originally real minicc --freestanding-compiled MiniC, milestone 21; rewritten to C along with the rest of the kernel). The loader's model is dead-simple (copy one contiguous byte range, jump to its first byte), which doesn't survive unmodified for compiled output: string literals land in .rodata and globals in .bss/.data, separate ELF sections that a normal multi-object link would scatter apart. Fixed with a build-step, not a compiler-level, change: the ring3 program gets its own standalone link (proc/ring3.ld, every section placed contiguously) and gets flattened with objcopy -O binary before being embedded — the loader itself never changed.

Real GCC inline asm has real operand binding, so do_syscall(num, arg1, arg2, arg3) loads its arguments straight into rax/rdi/rsi/rdx in one __asm__ block right before int 0x80 — a genuine simplification over the MiniC-era version, whose operand-less asm(...) had to stage every argument through global variables first.

A real, C-specific bug was found and fixed during the rewrite: spawn_process()'s loader always jumps to byte 0 of the loaded image — true by construction under MiniC's own single-pass codegen, which always placed the entry function first, but not guaranteed under gcc, which lays out .text in whatever order suits it. Confirmed via nm showing _start landing at a nonzero offset with a different function sitting at offset 0 instead — the CPU ran straight into that function's body as if it were the entry point. Fixed with a dedicated linker-script section (ring3.ld's .text.start) plus __attribute__((section(".text.start"))) directly on _start(), pinning it to offset 0 regardless of source order or any future gcc reordering.

Hardware discovery: PCI

Milestone 29 (Phase X's first step) is the first time this kernel discovers its own hardware instead of trusting a fixed, hardcoded I/O port — every earlier driver (VGA, serial, keyboard, PIT/PIC, ATA) just assumes its device sits at a well-known legacy address. That stops working the moment a device's location genuinely isn't fixed, which is exactly true of a NIC — networking's real prerequisite. drivers/pci.c walks the legacy CONFIG_ADDRESS/CONFIG_DATA mechanism (I/O ports 0xCF8/0xCFC, drivers/ io.c's new 32-bit outl/inl — PCI config space is dword-addressed) across all 32 device slots on bus 0, checking function 0 of each and only probing functions 1–7 for devices whose header-type byte marks them multi-function.

Deliberately scoped to bus 0 only — no recursion through a PCI-to-PCI bridge's secondary bus, since QEMU's default machine has none. A real bus walk would read a bridge's own secondary-bus-number register and recurse; that's a genuine but separate extension for whenever a device beyond bus 0 needs finding, not tackled here. There's also no general driver-registration/probe framework yet — finding a device by vendor:device ID today means a caller manually scanning g_pci_devices[].

Verified against something this kernel had no part in choosing: QEMU's own default machine model. Every device pci finds is a real, publicly-documented vendor:device ID pair — 0x8086:0x1237 (the i440FX host bridge), 0x8086:0x7000/0x7010/0x7113 (PIIX3 ISA bridge / IDE controller / PIIX4 ACPI bridge — 0x7010 is literally the same IDE controller disk/ata.c already talks to by hardcoded port), 0x1234:0x1111 (the Bochs/QEMU standard VGA device), and 0x8086:0x100e — a real Intel e1000 gigabit NIC, found with zero extra QEMU flags, and the next Phase X milestone's target device. See the Walkthrough for the real captured output.

The e1000 NIC driver

Milestone 30 is a real driver for the e1000 milestone 29 already found — deliberately scoped to initialization only: enable the device, map its registers, read back real hardware state. Setting up the RX/TX descriptor rings and moving an actual packet is a separably-sized hard problem, left for a later milestone — the same "narrowest safe first version" discipline bus-0-only PCI enumeration used.

Unlike every earlier driver in this kernel, the e1000's real register file isn't reached through port I/O — it's memory-mapped (MMIO). net/e1000.c enables the device over PCI (drivers/pci.c's new pci_config_write_dword() — this kernel's first PCI config space write, every earlier use was read-only — sets Memory Space + Bus Master in the command register), reads BAR0 (pci_read_bar0()) to find the device's real physical MMIO base, and maps 8 pages of it into the kernel's own address space via mm/paging.c's ordinary map_page() — the first time this kernel has mapped device registers rather than RAM, though the mapping mechanism itself doesn't distinguish the two.

A real assumption worth stating plainly, since it's the kind of thing that would fail badly and confusingly if wrong: BAR0 has to already hold a valid, assigned physical address for this to work at all. It does, because QEMU's -kernel boot still runs SeaBIOS first — multiboot loading is one of SeaBIOS's own jobs, not a BIOS bypass — so real PCI bus enumeration and BAR assignment already happened before this kernel ever got control. Confirmed empirically rather than assumed: a genuinely unassigned BAR would have meant mapping physical address 0 or garbage, and the driver would have read back nonsense instead of a real MAC address.

The MAC address comes straight from RAL0/RAH0 — pre-loaded by QEMU's own emulated EEPROM at power-on, the same way real hardware auto-loads its burned-in address — rather than implementing the separate EEPROM-read protocol (register EERD) just to re-derive a value already sitting in plain registers. Verified the same way milestone 29's own proof was: checkable against something this kernel had no part in choosing. The real MAC read back, 52:54:00:12:34:56, is QEMU's own well-known, publicly documented default NIC MAC — not a number this driver could fake its way into producing by accident — and the link-up bit reads a second, separate piece of real hardware state. See the Walkthrough for the real captured output.

Milestone 31 builds on that groundwork with real TX/RX descriptor rings and a genuine packet round trip — the DMA-buffer-management work milestone 30 deliberately deferred. A NIC doesn't move bytes through registers one at a time the way port I/O devices do: the driver hands the hardware a ring of descriptors (each a pointer to a real data buffer, plus length/status/command fields) living in ordinary RAM, and the device DMAs to/from those buffers itself once bus-mastering is enabled (already turned on in milestone 30). packed struct TxDescriptor/RxDescriptor match the hardware's own 16-byte layout exactly. e1000_send() copies data into a buffer, hands a descriptor to the hardware, and polls the descriptor's own DD (descriptor done) status bit — the hardware's own confirmation it genuinely completed the transmission, the same bounded-poll, fail-clean discipline disk/ata.c's ata_wait_ready/ata_wait_drq already established. e1000_receive() is the RX-side equivalent.

Deliberately not a real ARP subsystem — no address resolution cache, no general request/reply handling. The shell's new arp command crafts exactly one hardcoded, valid Ethernet+ARP request frame asking "who has 10.0.2.2" (QEMU's SLIRP networking's own well-known default gateway), purely as a real external stimulus to prove RX genuinely works — the same "one hardcoded test case, not a general framework" scope milestone 26's ring3fault already used.

A real fix found during testing, not assumed correct from the start: the first attempt's RX poll used a raw instruction-count spin bound, and got back nothing. Not a driver bug — a measurement one. A tight spin loop doesn't reliably correspond to any particular amount of real wall-clock time, and a genuine external SLIRP round trip needs real time to happen. Fixed by polling against isr/isr.c's own g_tick_count instead of a raw iteration count — the same underlying lesson this project's QEMU/TCG timer-rate gotcha already taught, applied to a new context.

Verified with the strongest proof this driver has produced yet: TX confirmed by the hardware's own descriptor-done bit, and RX confirmed by a genuine reply from QEMU's real, external network stack. from=52:55:0a:00:02:02/sender_ip=10.0.2.2 are QEMU's own documented default gateway MAC/IP — not anything this kernel could have fabricated. See the Walkthrough for the real captured output.

A real ARP resolver

Milestone 32 replaces milestone 31's own hardcoded one-shot ARP request/reply with a genuine resolver, built directly on the proven TX/RX plumbing rather than starting over. net/arp.c keeps a fixed-size cache (ArpEntry[8]) and exposes one real entry point, arp_resolve(ip, mac_out): check the cache first; only on a miss, send a real request and poll for a genuinely matching reply (right EtherType, right opcode, right sender IP — anything else that arrives is ignored, not mistaken for the answer) against a real g_tick_count-bounded timeout, the same lesson milestone 31 already learned about spin counts not reliably corresponding to real time.

Deliberately scoped as a client (resolver) only, not a responder — this kernel's own IP address (net/ip.c's g_my_ip, milestone 33) is a fixed, static assumption, not real DHCP-negotiated configuration, so answering "who has <our address>" for an address nothing actually negotiated doesn't mean much yet. The cache also has no eviction or TTL — a fixed-size table that just fills up, the same "narrowest safe first version" every driver-layer milestone in this phase has used.

The shell's arp command (same name milestone 31 used, now backed by the real mechanism) runs four checks in one pass, each independently checkable: resolve the gateway (a real external round trip, non-trivial elapsed ticks); resolve it again (zero elapsed ticks — a real, timing-based proof of the cache, not just "the same answer twice"); resolve a second, different real address (QEMU SLIRP's own DNS proxy, 10.0.2.3 — proving the resolver genuinely generalizes); and resolve an address nothing answers for (correctly returns false after the real timeout, not a hang). See the Walkthrough for the real captured output.

A real IP layer

Milestone 33 adds a real IPv4 layer, verified with a genuine ICMP echo (ping) round trip — the minimal, natural test vehicle for "does IP genuinely work end to end," the same relationship milestone 31's hardcoded ARP request had to proving TX/RX worked at all. A bare IP packet with no upper-layer protocol has nothing that could reply to it; ICMP echo is the smallest real protocol that gets an external, independently meaningful response.

net/ip.c holds ip_checksum() (the real RFC 791 one's-complement checksum — sum every 16-bit word, fold any carry back in, take the complement; the identical algorithm also covers ICMP) and ip_build_header() (a real 20-byte, no-options IPv4 header). It also holds g_my_ip — this kernel's own first real, named concept of "my IP address." Previously a bare literal duplicated inside net/arp.c's own request-building code, it's now one shared value both files use (still a fixed, static assumption — 10.0.2.15, QEMU SLIRP's conventional default guest address — not real DHCP-negotiated configuration; see Known limitations).

net/icmp.c's icmp_ping() resolves the target's MAC via milestone 32's real arp_resolve() first (a cache hit costs nothing here), builds a real Ethernet+IPv4+ICMP echo request, sends it, and polls — real g_tick_count- bounded, milestone 31/32's already-learned timing lesson — for a reply matching on every real field: EtherType, IP protocol, source IP, ICMP type, and the exact identifier/sequence number this specific request sent, not just "something ICMP arrived."

Verified in QEMU: ping gateway ok=0x1 elapsed_ticks=0x64 — a genuine reply from QEMU's real network stack, at the same non-trivial round-trip time arp already measured. A wrong IP header (a bad checksum, a malformed field) would most likely have gotten the packet silently dropped by QEMU's real host-level network stack rather than answered at all, so the reply arriving at all is itself strong indirect evidence the header was built correctly — the same "external validation beats self-validation" property every proof in this networking phase has looked for. See the Walkthrough for the real captured output.

A real UDP layer

Milestone 34 adds real UDP — the simpler of the two remaining transport protocols: no connection state, no retransmission or congestion control, just a port-addressed datagram wrapper over the now-working IP layer. TCP's real connection state machine, sequence numbers, and retransmission remain a substantially bigger, genuinely separate hard problem, left for a later milestone.

net/udp.c's udp_checksum() covers a 12-byte "pseudo-header" (source IP, dest IP, a zero byte, the protocol number, and the UDP length) plus the real UDP header and payload — binding the checksum to the addresses it's actually being delivered between, unlike IP's own header checksum, which covers only the 20 header bytes. It reuses ip.c's ip_checksum() algorithm unchanged by assembling the pseudo-header and message into one scratch buffer first. udp_send()/udp_receive() follow the exact same resolve-then-send-then-poll shape icmp_ping() already established.

net/dns.c's dns_query() is the real external verification vehicle — deliberately not a real DNS client (no response caching, no compression-pointer decoding, no record types beyond A), the same "one hardcoded real-protocol message as a test vehicle" discipline ARP's request and ICMP's ping both already used. It sends a minimal, hand-crafted query to QEMU SLIRP's own built-in DNS proxy (10.0.2.3, the same address arp already resolved in milestone 32) and verifies the exact transaction ID sent, the response (QR) bit, and a real answer count — proving SLIRP genuinely forwarded the query to a real upstream resolver and got a real answer back.

Verified in QEMU: dns query ok=0x1 elapsed_ticks=0x74 — noticeably higher than ping's own elapsed_ticks=0x64, a real, sensible detail: DNS resolution genuinely takes one more hop than ICMP echo (SLIRP forwards the query out and waits for a real reply, rather than answering directly the way it does for ping) — exactly the kind of small, correct-shaped detail that would be hard to fake by accident. See the Walkthrough for the real captured output.

A real TCP client

Milestone 35 adds real TCP — the first genuinely stateful transport protocol in this kernel, and the first time any protocol layer here has talked to a host off the local SLIRP subnet (every earlier target was the gateway at 10.0.2.2 or the DNS proxy at 10.0.2.3, both local). A real internet host doesn't answer ARP requests from this guest at all, so net/tcp.c's tcp_fetch() ARP-resolves the gateway's MAC for the Ethernet-level destination while putting the real remote IP in the IP header itself — routing, not resolution, decides an off-subnet frame's link-layer destination, the same distinction every real router relies on and the one genuinely new wrinkle this milestone had to get right that no earlier layer here ever needed to.

tcp_checksum() follows the identical pseudo-header shape udp_checksum() already established (protocol number 6 instead of 17). tcp_fetch() is deliberately scoped as a client only, one connection at a time, no connection table, no retransmission or congestion control — a real 3-way handshake (SYN, wait for a genuinely matching SYN-ACK with the right ACK number, then ACK), a real data segment carrying an actual HTTP/1.1 request, a receive loop that ACKs each arriving segment and keeps polling until the peer's FIN or the caller's buffer fills, and a best-effort graceful close that isn't required for the milestone's own success criterion. net/dns.c gained a real dns_resolve_a() alongside the existing dns_query() — it actually parses the answer section (a DNS-compression name pointer or a literal one, skipping past a CNAME if one leads) instead of only checking the header, so the TCP demo's target is a freshly-resolved real IP, not a hardcoded address that could go stale.

Verified in QEMU, twice, independently: two different real IPs for example.com (Cloudflare's own round-robin DNS, both confirmed via a real curl from the same environment) — tcp_fetch_ok=0x1 response_len=0x200 got_http_status=0x1 both times, a complete handshake, a full 512-byte real HTTP response (the receive buffer's own cap — the real reply was at least that long), and a confirmed real HTTP status line at the start of it, not just "some bytes arrived." tasks run immediately afterward confirmed the scheduler and every other kernel task stayed healthy through the exchange. See the Walkthrough for the real captured output.

Testing methodology

Every claim in this project is backed by a concrete, checkable assertion — never just "it didn't crash." An exact byte count matching hand arithmetic, a register value read back and printed (proving real CPL 3, not just "a syscall happened"), a physical address that genuinely differs between two isolated processes mapping the identical virtual address, a frame-allocator count identical before and after an operation that must not leak. See the Walkthrough for what these look like in practice.

Testing runs in QEMU, headless, with serial output redirected to a file and keystrokes sent over the monitor socket: 

qemu-system-x86_64 -kernel kernel.elf -display none \
    -serial file:serial.log -monitor unix:/tmp/qmon,server,nowait \
    -drive file=disk.img,format=raw,if=ide -no-reboot
echo 'sendkey h' | nc -U /tmp/qmon   # types 'h'
echo 'sendkey spc' | nc -U /tmp/qmon # space
echo 'sendkey ret' | nc -U /tmp/qmon # enter

Known limitations (on purpose, for now)

  • The shared identity-map/heap region is still fully user-accessible — fixed in milestone 26: a cloned address space's copy of PDPT[0]/PDPT[1] has the user bit stripped, verified with a real forbidden-write page fault (see Memory protection). Real isolation now covers both the private per-process region and direct ring3 access to the shared one — everything ring3 code still legitimately needs there goes through a syscall instead.
  • Pointer arguments (paths, buffers) are checked for validity/bounds but not ownership — nothing stops a ring3 process from passing a pointer that doesn't actually belong to it. Both channel (milestone 25) and process (milestone 27) handles are now real, rights-checked capabilities (see Capabilities & rights) — but process only has one real right (RIGHT_QUERY) to enforce so far, since there's no second Process operation (like a real terminate/kill) yet to need a second one.
  • No process teardown/exit exists at all — fixed in milestone 37 (see Process model & isolation): a real process_exit syscall, verified with ps's own exited=0x field. Nothing is reclaimed when a process exits — frames fixed in milestone 39: image, stack, and page-table frames plus the process's own PML4/PDPT are all freed, verified against exact frame-count arithmetic. The process/task table slot stays occupied forever — fixed in milestone 40: the next spawn reuses an exited slot (and its already-allocated kernel stack) instead of growing the table, verified across repeated restart cycles never growing ps's process count. g_objects[8] (the kernel object table) isn't reclaimed at all — fixed in milestone 41: process_exit now frees every object referenced by the exiting process's own handle table, verified with objs matching exact hand arithmetic and the milestone-40 regression scenario re-run clean. A handle another process holds to a still-running process has no way to be released early — fixed in milestone 42: a new handle_close syscall lets the holder free one of its own handles (and the object behind it) without exiting, verified by looping init's restart of hello_service 3 times with a close after each cycle and confirming objs returns to the exact clean-boot baseline every time. Still open: any handle still pointing at an exited-then-reused process slot now points at a different, live process, not just a frozen dead one - a sharper, more real version of the same "no ownership on handles" gap elsewhere on this list.
  • spawn_builtin's program registry is a single fixed, compile-time entry — fixed in milestone 43: a new register_service syscall lets a ring3 process load a VFS file into one of 4 runtime registry slots and get back an index spawn_builtin can launch alongside the one fixed compile-time entry, verified by registering and launching the boot demo's own binary at runtime and confirming the resulting process's self-query matches. No unregister_service, so those 4 slots are a lifetime cap per boot — fixed in milestone 44: a new unregister_service syscall frees a slot for genuine reuse, verified by registering, unregistering, confirming spawn_builtin on that index now fails, then re-registering and confirming the exact same index and a working spawn. Still open: unregister_service doesn't check that the caller is the one who registered the slot — any process can unregister any slot, the same pointer/resource-ownership gap documented elsewhere on this list, not closed by this milestone. init.c restarts its one service exactly once (milestone 38) — a real restart-on-exit proof, but not a real supervisor: no restart limit/backoff, no dependency ordering, and a second restart would fail outright once the fixed 4-slot process table fills (see the process-table limitation below).
  • No NX (no-execute) enforcement anywhere — fixed in milestone 28 for every dynamically-mapped pure-data region, including every ring3 process's own user stack (see Memory protection). Still open: a loaded ring3 program's own code+data image stays entirely executable — the loader flattens a whole compiled program into one contiguous blob with no tracked code/data boundary, so a real W^X split within a loaded image is a separate, larger problem. ASLR and true process sandboxing (beyond the address-space isolation that's existed since milestone 12) remain two more genuinely different, completely unscoped mechanisms — not silently forgotten, just not yet tackled.
  • Every fixed-size table in this kernel (tasks, processes, objects, handles, channels, mounts) has a small, arbitrary capacity, and most creation calls at boot don't check their own return value for success — harmless today (nothing is near its cap), a real bug class once boot-time setup grows further.
  • MiniFS is deliberately simple — flat namespace (no directories), a fixed 16-file cap, no delete/truncate/append, no journaling (a crash mid-write leaves partial state), and files can't safely be overwritten (only created fresh).
  • The ATA driver only supports the primary bus's master drive, polling rather than interrupt-driven — no secondary bus, no slave, no AHCI/NVMe.
  • No PCI enumeration — fixed in milestone 29 for bus 0 (see Hardware discovery: PCI). Still open: no bridge recursion beyond bus 0, no general driver-registration framework. disk/ata.c also hasn't been retrofitted to use PCI discovery instead of its own hardcoded 0x1F0, even though pci now finds that exact same controller.
  • No NIC driver, no packet TX/RX — both fixed as of milestones 30-31 (see The e1000 NIC driver): the e1000 is PCI-enabled, MMIO-mapped, and moves real packets through real TX/RX descriptor rings, verified with a genuine external round trip through QEMU's own network backend. No real ARP subsystem — fixed in milestone 32 (see A real ARP resolver): a genuine cache, arp_resolve() for any target address. No IP layer — fixed in milestone 33 (see A real IP layer): real IPv4 header construction, a real RFC 791 checksum, and a genuine ICMP echo round trip. No UDP — fixed in milestone 34 (see A real UDP layer): real pseudo-header checksums, verified with a genuine DNS query to QEMU's own resolver proxy. Still fully open: ARP remains client-only (no responder). This kernel's own IP address (g_my_ip) is a fixed, static assumption, not real DHCP-negotiated configuration. The ARP cache has no eviction/TTL. No TCP — fixed in milestone 35 (see A real TCP client): a real 3-way handshake, real data exchange, and a genuine HTTP round trip to an actual internet host. Still open: no retransmission or congestion control at all (a lost segment just times out), client-only (no listening/server side), one connection at a time with no connection table, no options (no window scaling, no SACK), and close is best-effort only. ICMP is the only IP-layer protocol implemented, and only its echo request/reply message type at that. net/dns.c's dns_query() is deliberately not a real DNS client — no caching, no record types beyond A — it exists purely as an external test vehicle for UDP (dns_resolve_a(), added for TCP's own real target resolution, does real answer-section parsing but still only ever asks for one A record, no retry, no multiple questions). The rings are fixed-size (8 descriptors each), and both TX/RX poll rather than using the device's own interrupt capability — the same "poll first, interrupts later" precedent disk/ata.c already established.
