Architecture

How MiniC OS is built

Almost everything past the boot transition is ordinary, hand-written freestanding C. The only hand-written x86 assembly is what's genuinely below what a C function body (even real GCC inline asm, which has real operand binding) can express: program structure, not logic — the 32-to-64-bit boot transition, interrupt entry stubs, and context switching.

This kernel was originally built in MiniC, a small hand-rolled language with its own compiler, then rewritten by hand into freestanding C for faster day-to-day development — the architecture and verification bar didn't change, only the implementation language did. This page describes the kernel's current C implementation throughout.

Boot process

Multiboot1 drops the kernel in 32-bit protected mode; this kernel runs in 64-bit long mode. Getting from one to the other — loading a GDT, building page tables, enabling long mode, far-jumping into a 64-bit code segment — is hand-written in boot/boot.s, the same way every kernel project does it, even ones written in Rust or Zig. boot/linker.ld places the multiboot header and code at the conventional 1MB load address multiboot expects.

QEMU's multiboot1 -kernel loader hard-rejects a genuine ELF64 image ("Cannot load x86-64 image, give a 32bit one"), so every object — hand-written .s and gcc-compiled .c alike — still links as ld -m elf_i386 even though the code inside runs in real 64-bit long mode: each .c file compiles to assembly, gets a literal .code64 directive prepended, and is fed to as --32, which encodes the 64-bit mnemonics correctly while keeping the ELF32 container format. Two gcc flags this pipeline specifically needs: -fPIC (otherwise a global's absolute 64-bit address needs a relocation type unrepresentable in an ELF32 table) and -fvisibility=hidden (otherwise a reference to an external symbol routes through the GOT via an ELF64-only relocation syntax as --32 can't parse — every header wraps its declarations in #pragma GCC visibility push(hidden)/pop).

boot.s also owns the GDT/TSS setup: a ring3 code/data segment pair alongside the ring0 ones, and a TSS whose RSP0 field tells the CPU which stack to switch to on any ring3→ring0 transition. RSP0 is an absolute reset point, not a continuation — the CPU loads it fresh on every transition, so pointing it at a stack something else is still using silently corrupts that other thing's state. boot.s sets it once, to its own dedicated stack, as a safe initial value; from the process model onward (see below), the scheduler repoints it per-task on every context switch instead.

Once in 64-bit mode, boot.s calls the kernel's own entry point, _start() in kmain.c — everything past that point is ordinary freestanding C: volatile, packed struct, pointer arithmetic, and real GCC inline asm for the handful of raw instructions C has no other way to express: out/in/lidt/sti/ invlpg, reading cr2/cr3.

Scheduler

A fixed table of tasks, each with its own kalloc'd stack. create_task() hand-builds a new task's initial stack to look exactly like what the hand-written switch_context() would have left behind, with the task's entry point as a fake "return address" — the first switch into a never-run task lands there via an ordinary ret, no special-casing needed for "first run" vs "resuming."

yield() round-robins to the next non-blocked task — called voluntarily by cooperative tasks, and also called from inside the timer interrupt handler, which is what makes scheduling preemptive: since the interrupt handler is just an ordinary nested C call on whichever task's stack the CPU happened to interrupt, calling yield() from inside it suspends that call exactly like a voluntary yield() would.

sleep(ticks) adds real blocking: a task marks itself blocked with a wake tick and yields away; the scan skips blocked tasks, waking one up the moment its condition is met. Every other blocking primitive in this kernel - channel receive (see IPC below), and every async I/O wait (see Async file I/O/Async networking) - reuses the exact same mechanism rather than inventing a separate one each time: a task's own waiting_on field is either NULL (blocked on the tick check above) or points at whatever real bool flag needs to become true - a channel's own full field, a pending request's own done field. yield()'s wake check is a single dereference of that pointer when it's set, so adding a new blocking primitive never needs a new dedicated field or a new branch in the scheduler - just point waiting_on at the right flag.

Process model & isolation

Real per-process address-space isolation: clone_address_space() builds a fresh PML4 whose entry 0 points at a fresh PDPT that shares PDPT[0]/PDPT[1] (identity map + heap) with the kernel's own PDPT — literally the same physical sub-tables, so kernel code/stack/heap stay reachable unchanged — while everything from PDPT[2] up starts out not-present, private to whichever task gets that PML4.

spawn_process(image_start, image_end, load_vaddr, stack_vaddr) is the real loader: clones a fresh address space, maps and copies a byte range into it page by page, maps a user stack, then creates a scheduler task whose kernel-mode entry does exactly one thing — enter ring3 at the loaded address via a hand-written fake-iretq-frame trick. From then on the task only ever runs in ring3, preemptible by the timer like any other task. spawn_process_from_path(path, ...) is the same loader fed from a real file read through the VFS instead of a pointer range.

A kernel-wide kernel_object table plus a separate per-process handle table give ring3 code a small integer instead of a raw kernel pointer — resolve_handle(process_index, handle) is the one place that integer becomes a real object index, bounds- checked and existence-checked, never trusted directly. Every process gets a handle to itself for free, guaranteed to land in the well-known slot 0 (a fresh handle table starts empty, so the first allocation into it always takes slot 0).

A third way to spawn a process sits alongside the two above: spawn_builtin (syscall 11) lets a ring3 process spawn another ring3 process from a program registry addressed by index rather than a raw pointer or a filesystem path — one fixed, kernel-embedded entry (hello_service.c), plus up to 4 runtime-registered slots (see below). This is what proc/init.c — the kernel's first real init process, spawned by kmain.c at boot the same way the existing demo process always has been — uses to launch proc/hello_service.c without needing the filesystem to have anything on it yet (a fresh disk.img is empty until mkfs+install run manually). The registry is intentionally not a raw-pointer API: letting ring3 code name an arbitrary address as "a program to run" would undo the real work the capability/rights model elsewhere in this kernel puts into making sure ring3 code can only ever act through something the kernel already vetted. register_service (syscall 14) lets a ring3 process load a VFS file into one of those 4 runtime slots at runtime and get back an index spawn_builtin can address the same way as the fixed entry; unregister_service (syscall 15) frees a slot for genuine reuse — verified by registering, unregistering, confirming a subsequent spawn_builtin on that index now correctly fails, then registering again and getting back the exact same index before spawning it successfully. Registering/unregistering a slot never affects a process already spawned from it, since spawn_process() copies the image into the new process's own address space at spawn time rather than referencing the registry slot afterward. Deliberately doesn't track which process registered a slot, so any process can unregister any slot — matches this kernel's existing pointer-ownership gap (see Known limitations) rather than closing it.

A process's real lifecycle closes with process_exit (syscall 12): the calling task marks its own task and process table slots as no-longer-alive, then yields away for the last time. sched/task.c's scheduler scan permanently skips a slot marked this way — the exact same shape it already uses to skip a temporarily blocked task, just with no wake condition that will ever fire. proc/hello_service.c calls process_exit() right after its own startup message instead of idling forever, and the ps shell command's exited=0x field per process makes this directly observable — a fresh boot shows the boot-time demo and init both exited=0x0 while hello_service alone shows exited=0x1, immediately and every time.

Exiting genuinely reclaims everything tied to the process rather than just marking it dead. A mm/paging.c function, free_address_space(pml4_phys), walks the exiting process's own page tables (PDPT[2..511] -> PD -> PT - the private per-process region; PDPT[0]/[1], the shared kernel/heap sub-tables, are never touched), freeing every present leaf frame plus the PT/PD frames themselves, then the process's own PDPT and PML4 frames. Safe to call from inside process_exit() even though it tears down the caller's own address space: the syscall runs in kernel mode on the shared identity map throughout, and CR3 only actually moves off the freed PML4 once yield()'s own load_cr3() runs immediately after. Verified with real diagnostic prints of g_free_frame_count around the free: repeated exit cycles return the free count to the identical baseline every time, not drifting.

The process/task table slot itself is also reused: spawn_process() and create_task_with_cr3() search for an exited slot before appending, so the table no longer only ever grows. create_task_with_cr3() returns the real task index (or -1 on failure) rather than a bare success/fail flag, since a reused slot's index can't be inferred as "whatever the counter currently is" the way an always-appended one could. A reused task slot reuses its old kalloc'd kernel stack directly rather than allocating a fresh one - just reinitializes the fake switch-frame at the top of the same block - sidestepping "freeing your own currently-executing stack from within itself" entirely instead of solving it, and meaning reuse doesn't leak heap memory either. Verified in QEMU: the same task_index/cr3 come back for a restart every time, and ps never grows past the real process count across repeated spawn/exit cycles.

The exiting process's own kernel-object handle table is reclaimed too, via free_object()/free_handle() in proc/object.c: process_exit walks the exiting process's own handle table and frees every object it referenced. alloc_object()/alloc_handle() already scanned for a free slot before appending — they simply needed something freed to find. The scope is deliberately narrow: a handle another process holds to the exiting one — init's own permanent open_process handle onto hello_service, for instance — lives in that other process's own table, not the exiting process's, so exit alone doesn't touch it. handle_close (syscall 13) closes that gap: it validates a handle belongs to the caller and is currently in use, then calls the same free_object()/free_handle() pair — a second entry point into the same reclaim mechanism that doesn't require exiting first. init.c uses this to close its own query handle onto hello_service after each restart cycle, so a real restart loop doesn't slowly exhaust the shared kernel object table. Verified in QEMU: objs returns to the exact clean-boot baseline after a full spawn/exit/restart/exit cycle and after several rounds of open/query/close/restart — zero net object growth, not just a smaller leak — and matches hand arithmetic exactly at every step.

IPC (channels)

A channel is a single-slot mailbox (one u64 message). channel_send() is non-blocking — fails outright if the mailbox is already full, rather than overwriting an unread message or blocking the sender too (a real, separate hard problem, not tackled yet). channel_receive() is the one genuinely new scheduler mechanism: it blocks the calling task exactly the way sleep() already does, just with a channel index set instead of a wake tick — the blocked-task scan gained a second wake condition (a message arriving) alongside the tick check.

Async file I/O

Every other I/O path in this kernel is fully synchronous - the calling task sits idle for the operation's entire duration, whether it's a disk read/write or a network round trip. File reads and writes are the exception: a process can issue one and get back a handle immediately, do other real work, then collect the result only when it actually needs it.

proc/io_request.c holds a fixed pool of 4 pending- request slots, each with its own 512-byte kernel-owned buffer, serviced by one dedicated kernel worker task (io_worker_entry(), created at boot like any other plain kernel task). The "async" part comes from cooperative multitasking, not hardware DMA/interrupts - the ATA driver is PIO-only, so the worker task's own vfs_read()/ vfs_write() call genuinely runs concurrently with the caller only in the sense that ordinary preemptive scheduling interleaves them, the same mechanism behind every other concurrent thing this kernel does.

Syscall 16, file_read_async, copies the requested path into the request slot's own kernel memory - the caller's path pointer usually points into its own private ring3 image (a string literal, for instance), which isn't safely dereferenceable from the worker task's own kernel CR3 once several scheduler switches have passed - then returns a real kernel-object handle immediately, without waiting for anything. Syscall 17, file_read_wait, is where blocking actually happens: it resolves the handle, and if the worker hasn't finished yet, blocks the caller via sched/task.c's generic wake-condition mechanism (see Scheduler) - the exact same primitive channel_receive() already uses, not a busy spin - then copies from the worker's scratch buffer into the caller's own buffer and frees the request slot, object, and handle together. Syscalls 18/19, file_write_async/file_write_wait, are the same shape in reverse: the write payload is copied into the request's own kernel buffer at issue time (same dereferenceability reasoning as the path), and the wait syscall just returns the byte count once the worker's own vfs_write() completes - no data flows back, so no copy-out step. Each wait syscall rejects a handle issued by the other operation, since both share the same OBJ_IO_REQUEST object type.

Verified in QEMU, twice each: for reads, the boot-time demo process issues an async read of a file it already read synchronously earlier in its own startup sequence, does 5 rounds of real work (prints) before waiting, then collects the result - all 5 prints land before the wait unblocks, proving the process genuinely wasn't stalled, and the async read's own byte count and buffer content exactly match the earlier synchronous read of the same file. For writes, the demo issues an async write, does 5 more rounds of real work, waits, then reads the file straight back through the already-proven synchronous path - a real round trip, not just a plausible-looking byte count, and independently checkable even against the pre-existing intermittent vfs_write() return-value flake (see Known limitations): one run hit that exact flake on file_write_wait's own return value, and the verify-read still confirmed the data landed correctly. objs returns cleanly afterward every run, confirming the request slot, object, and handle are all actually freed rather than leaked. Deliberately narrow: a fixed 4-request pool with a 512-byte cap per operation.

Async networking: the first ring3-facing network capability

Every network operation in this kernel - ARP, ICMP, UDP, DNS, TCP - was a kernel-mode shell command only, with zero ring3-facing syscall of any kind. Rather than exposing a synchronous version first, both ICMP ping and DNS resolution go straight to async, the same shape as the file operations above: a process issues one and gets back a handle immediately, does other real work, then collects the result only when it needs it.

proc/net_request.c holds its own small pool - 2 pending-request slots - serviced by a separate dedicated worker task (net_worker_entry()) from the file-I/O one. Deliberately not shared with file I/O: both icmp_ping() and dns_resolve_a() have their own internal timeouts that can run up to 2000 ticks, and one worker servicing both domains would let a slow network operation stall a pending file operation (or vice versa) for that entire window. Ping and DNS do share this one pool/worker with each other, unlike the file/network split - both are single-round- trip requests of similar timeout scale, so an is_dns flag on each slot (the same shape io_request's own is_write flag already established) is enough to tell the worker which real function to call. Syscall 20, net_ping_async, packs the target IP into a single argument; syscall 22, net_dns_async, copies the hostname into the slot at issue time (same dereferenceability reasoning as every other async issue call). Both return a handle immediately. Syscall 21 (net_ping_wait) and syscall 23 (net_dns_wait, which also copies the resolved 4-byte IP into the caller's own buffer on success) block via the same generic wake-condition mechanism every blocking primitive in this kernel now shares (see Scheduler). Each wait syscall rejects a handle issued by the other network operation, same guard as the file read/write pair.

A real, small correctness improvement came along with this: net/arp.c's arp_resolve(), net/icmp.c's icmp_ping(), and net/udp.c's udp_receive() (which dns_resolve_a() is built on) now call yield() inside their own poll loops, not just relying on the timer to force a switch eventually. All three routinely run for hundreds of ticks and are now regularly invoked from a background worker task on another process's behalf - cooperating with the scheduler instead of just waiting to be interrupted is the right default there, matching io_worker_entry()'s own already-established pattern. This changes nothing about the existing kernel-mode ping/arp/ dns/tcp commands' own behavior - confirmed with a full regression pass.

Verified in QEMU, twice each: for ping, the boot-time demo process issues an async ping to QEMU's real gateway (10.0.2.2, the same target the kernel-mode ping command uses), does 5 rounds of real work before waiting for it - all 5 prints land before the wait unblocks, and the wait resolves with a genuine successful round trip to QEMU's real network backend. A regression pass confirmed the kernel-mode ping/arp commands still work correctly afterward - one run's follow-up ping even showed elapsed_ticks=0x0, a real cross-check that the ARP cache entry the async ping's own arp_resolve() call populated was genuinely shared and reused. For DNS, the demo resolves example.com - the same hostname the existing kernel-mode TCP demo already targets - asynchronously, and gets back a real IP both runs (104.20.23.154 and 172.66.147.243, Cloudflare's own round-robin DNS). The second run's own follow-up tcp command independently resolved the identical address via its own separate dns_resolve_a() call in the same boot - a genuine cross-check, not a coincidence - and tcp_fetch_ok=0x1 confirmed no regression from the udp_receive() yield() addition. objs returns cleanly after every run. Deliberately narrow: ping and DNS only - no async ARP/UDP/TCP for ring3 yet, and those protocols still have no ring3-facing syscall at all.

Capabilities & rights

Every handle carries a rights bitmask, set once when the handle is granted and never widened afterward: 

const int RIGHT_QUERY = 1;
const int RIGHT_SEND = 2;
const int RIGHT_RECEIVE = 4;

open_channel (syscall 9) is the one place a ring3 process can turn a raw channel index into a handle — and the one place the kernel decides policy: it always grants RIGHT_RECEIVE only, regardless of what the caller might want, since nothing in this kernel today needs a ring3-initiated send (the shell always sends directly, in kernel mode). channel_send/ channel_receive check the calling handle's rights before ever touching the underlying channel — a handle obtained through open_channel genuinely cannot be used to send, not just "isn't expected to." See the Walkthrough for a real rejected send attempt.

Real enforcement extends to process handles too. RIGHT_QUERY is granted to every process's own self-handle, and syscall 3 checks it before resolving any OBJ_PROCESS handle, using the same inline check syscalls 7/8/9 use. open_process (syscall 10) is the real cross-process capability — given another task's index, it mints a handle to that process in the caller's own table, granting the intersection of a caller-requested rights bitmask and what's actually grantable. Requesting 0 still returns a real, valid handle — just one that can do nothing, which is what the negative-space proof actually exercises: a handle opened with no rights genuinely fails to query, while a second handle to the same process opened with RIGHT_QUERY succeeds and reports the correct task_index. See the Walkthrough for the real captured proof.

Memory protection: the shared region, and NX

clone_address_space() (mm/paging.c) strips the user (0x04) bit from its copy of the kernel's own PDPT[0]/PDPT[1] entries when building a new address space — x86 paging ANDs that bit across every level from PML4 down to the leaf, so a supervisor-only leaf mapping underneath doesn't matter if an intermediate PDPT entry above it is user-accessible. The exploitable surface turned out to be narrower than it might look — the heap and the map demo command already pass leaf flags without the user bit, so the gap this closes is specifically boot.s's static 1GB identity map's 2MB huge-page leaves (PDPT index 0).

The fix strips the user bit from the copy clone_address_space() makes — boot.s's own tables and the kernel's original address space (g_pml4_phys, used directly by plain kernel tasks that never enter ring3) are untouched. Every legitimate ring3 interaction with this region already goes through a syscall, which raises CPL to 0 before touching kernel memory or the heap — nothing in this kernel needed direct ring3 access to begin with.

Verified with a genuine negative-space proof, not just a topology change: the shell's ring3fault command sends a second trigger value on the existing ring3-demo channel, causing the boot-time process to deliberately attempt a forbidden write to 0x100000 (the kernel's own multiboot load address — present, and never mapped by that process itself). The existing page-fault handler reports the exact faulting address and halts, before the process's own "it worked" print can ever run. See the Walkthrough for the real captured output.

Real NX (no-execute) enforcement — the classic W^X hardening that stops injected "shellcode" from being jumped to and run — is also in place. boot.s sets EFER.NXE (bit 11) at boot, in the same rdmsr/ wrmsr round trip as the existing EFER.LME — order matters, since setting a page table entry's NX bit (PTE bit 63) before NXE is live is a reserved-bit violation on every access to that page, not an execute-only restriction. Unlike the "user" bit above (which the CPU ANDs across every translation level, so an intermediate PDPT entry had to be fixed), the CPU ORs the NX bit across every level — only the final leaf PT entry ever needs it set, no intermediate-table change required. Applied to every dynamically-mapped region that's genuinely pure data: the heap, the map demo, the scheduler's private demo mapping, and — the real point — every ring3 process's own user stack. Deliberately not applied to a loaded ring3 program's own code+data image: the loader still flattens a whole compiled program into one contiguous blob with no tracked code/data boundary (see Compiled C in ring 3), so a real W^X split within a loaded image remains open — see Known limitations.

Verified with a real negative-space proof again: the shell's ring3nx command has the boot-time process write a real ret opcode (0xC3) onto its own stack and attempt to call it. The page fault's error code — 0x15 — has the CPU's own instruction-fetch bit (bit 4) set, independently distinguishing this from ring3fault's own write-violation error code (0x7). See the Walkthrough for the real captured output.

The native API

Ring3 processes are real, gcc-compiled C programs (see below), and the native API is a plain C function taking an explicit self pointer wrapping the syscalls above — not raw syscall numbers, and not method-call syntax (that was a MiniC-era feature; self.method(args) becomes type_method(&self, args) in C).

file — whole-file, path-based (no open/close/seek at the kernel level)
typedef struct { char* path; } file;

u64 file_write(file* self, char* buf, u64 len);
u64 file_read(file* self, char* buf, u64 max_len);

bool channel_send(channel* self, u64 value);           // fails without RIGHT_SEND

typedef struct { char* path; } process;

// returns the new process's task index, or -1

bool process_handle_open(process_handle* self, int task_index, int requested_rights);

u64  process_handle_query(process_handle* self);

The POSIX-shaped shim

open/read/write/close — plain free functions, deliberately not methods, matching POSIX's real API shape rather than extending the native OO-style one. Implemented entirely in ring3 C, with no new syscalls and no kernel changes: since file is whole-file only, open() loads (or starts) a per-fd in-memory buffer once, read()/write() serve out of it while advancing a position cursor, and close() flushes a written buffer through file.write() in one shot. 

int open(char* path, int mode);   // 0 = read, 1 = write (create)
int read(int fd, char* buf, int len);
int write(int fd, char* buf, int len);
int close(int fd);
A real, small gap from true POSIX: only one open-for-write "session" can safely target a given path at a time — there's no kernel-side file-descriptor concept backing this, just a per-process in-memory table.

Compiled C in ring 3

Ring3 programs are real, gcc-compiled C — not hand-assembled machine code (originally real minicc --freestanding-compiled MiniC; rewritten to C along with the rest of the kernel). The loader's model is dead-simple (copy one contiguous byte range, jump to its first byte), which doesn't survive unmodified for compiled output: string literals land in .rodata and globals in .bss/.data, separate ELF sections that a normal multi-object link would scatter apart. Fixed with a build-step, not a compiler-level, change: the ring3 program gets its own standalone link (proc/ring3.ld, every section placed contiguously) and gets flattened with objcopy -O binary before being embedded — the loader itself never changed.

Real GCC inline asm has real operand binding, so do_syscall(num, arg1, arg2, arg3) loads its arguments straight into rax/rdi/rsi/rdx in one __asm__ block right before int 0x80 — a genuine simplification over the MiniC-era version, whose operand-less asm(...) had to stage every argument through global variables first.

A real, C-specific bug was found and fixed during the rewrite: spawn_process()'s loader always jumps to byte 0 of the loaded image — true by construction under MiniC's own single-pass codegen, which always placed the entry function first, but not guaranteed under gcc, which lays out .text in whatever order suits it. Confirmed via nm showing _start landing at a nonzero offset with a different function sitting at offset 0 instead — the CPU ran straight into that function's body as if it were the entry point. Fixed with a dedicated linker-script section (ring3.ld's .text.start) plus __attribute__((section(".text.start"))) directly on _start(), pinning it to offset 0 regardless of source order or any future gcc reordering.

Hardware discovery: PCI

This is the first place this kernel discovers its own hardware instead of trusting a fixed, hardcoded I/O port — every earlier driver (VGA, serial, keyboard, PIT/PIC, ATA) just assumes its device sits at a well-known legacy address. That stops working the moment a device's location genuinely isn't fixed, which is exactly true of a NIC — networking's real prerequisite. drivers/pci.c walks the legacy CONFIG_ADDRESS/CONFIG_DATA mechanism (I/O ports 0xCF8/0xCFC, drivers/ io.c's new 32-bit outl/inl — PCI config space is dword-addressed) across all 32 device slots on bus 0, checking function 0 of each and only probing functions 1–7 for devices whose header-type byte marks them multi-function.

Deliberately scoped to bus 0 only — no recursion through a PCI-to-PCI bridge's secondary bus, since QEMU's default machine has none. A real bus walk would read a bridge's own secondary-bus-number register and recurse; that's a genuine but separate extension for whenever a device beyond bus 0 needs finding, not tackled here. There's also no general driver-registration/probe framework yet — finding a device by vendor:device ID today means a caller manually scanning g_pci_devices[].

Verified against something this kernel had no part in choosing: QEMU's own default machine model. Every device pci finds is a real, publicly-documented vendor:device ID pair — 0x8086:0x1237 (the i440FX host bridge), 0x8086:0x7000/0x7010/0x7113 (PIIX3 ISA bridge / IDE controller / PIIX4 ACPI bridge — 0x7010 is literally the same IDE controller disk/ata.c already talks to by hardcoded port), 0x1234:0x1111 (the Bochs/QEMU standard VGA device), and 0x8086:0x100e — a real Intel e1000 gigabit NIC, found with zero extra QEMU flags. See the Walkthrough for the real captured output.

The e1000 NIC driver

A real driver for the e1000 PCI enumeration finds — enables the device, maps its registers, and reads back real hardware state, on top of real RX/TX descriptor rings that move actual packets.

Unlike every earlier driver in this kernel, the e1000's real register file isn't reached through port I/O — it's memory-mapped (MMIO). net/e1000.c enables the device over PCI (drivers/pci.c's pci_config_write_dword() — a real PCI config space write, not just a read — sets Memory Space + Bus Master in the command register), reads BAR0 (pci_read_bar0()) to find the device's real physical MMIO base, and maps 8 pages of it into the kernel's own address space via mm/paging.c's ordinary map_page() — the first time this kernel has mapped device registers rather than RAM, though the mapping mechanism itself doesn't distinguish the two.

A real assumption worth stating plainly, since it's the kind of thing that would fail badly and confusingly if wrong: BAR0 has to already hold a valid, assigned physical address for this to work at all. It does, because QEMU's -kernel boot still runs SeaBIOS first — multiboot loading is one of SeaBIOS's own jobs, not a BIOS bypass — so real PCI bus enumeration and BAR assignment already happened before this kernel ever got control. Confirmed empirically rather than assumed: a genuinely unassigned BAR would have meant mapping physical address 0 or garbage, and the driver would have read back nonsense instead of a real MAC address.

The MAC address comes straight from RAL0/RAH0 — pre-loaded by QEMU's own emulated EEPROM at power-on, the same way real hardware auto-loads its burned-in address — rather than implementing the separate EEPROM-read protocol (register EERD) just to re-derive a value already sitting in plain registers. Verified the same way PCI enumeration's own proof was: checkable against something this kernel had no part in choosing. The real MAC read back, 52:54:00:12:34:56, is QEMU's own well-known, publicly documented default NIC MAC — not a number this driver could fake its way into producing by accident — and the link-up bit reads a second, separate piece of real hardware state. See the Walkthrough for the real captured output.

Real TX/RX descriptor rings back a genuine packet round trip. A NIC doesn't move bytes through registers one at a time the way port I/O devices do: the driver hands the hardware a ring of descriptors (each a pointer to a real data buffer, plus length/status/command fields) living in ordinary RAM, and the device DMAs to/from those buffers itself once bus-mastering is enabled. packed struct TxDescriptor/RxDescriptor match the hardware's own 16-byte layout exactly. e1000_send() copies data into a buffer, hands a descriptor to the hardware, and polls the descriptor's own DD (descriptor done) status bit — the hardware's own confirmation it genuinely completed the transmission, the same bounded-poll, fail-clean discipline disk/ata.c's ata_wait_ready/ata_wait_drq already established. e1000_receive() is the RX-side equivalent.

A real fix found during testing, not assumed correct from the start: the first attempt's RX poll used a raw instruction-count spin bound, and got back nothing. Not a driver bug — a measurement one. A tight spin loop doesn't reliably correspond to any particular amount of real wall-clock time, and a genuine external SLIRP round trip needs real time to happen. Fixed by polling against isr/isr.c's own g_tick_count instead of a raw iteration count — the same underlying lesson this project's QEMU/TCG timer-rate gotcha already taught, applied to a new context.

Verified with the strongest proof this driver has produced yet: TX confirmed by the hardware's own descriptor-done bit, and RX confirmed by a genuine reply from QEMU's real, external network stack. from=52:55:0a:00:02:02/sender_ip=10.0.2.2 are QEMU's own documented default gateway MAC/IP — not anything this kernel could have fabricated. See the Walkthrough for the real captured output.

A real ARP resolver

A genuine resolver, built directly on the proven TX/RX plumbing. net/arp.c keeps a fixed-size cache (ArpEntry[8]) and exposes one real entry point, arp_resolve(ip, mac_out): check the cache first; only on a miss, send a real request and poll for a genuinely matching reply (right EtherType, right opcode, right sender IP — anything else that arrives is ignored, not mistaken for the answer) against a real g_tick_count-bounded timeout, since a spin loop doesn't reliably correspond to real time.

Deliberately scoped as a client (resolver) only, not a responder — this kernel's own IP address (net/ip.c's g_my_ip) is a fixed, static assumption, not real DHCP-negotiated configuration, so answering "who has <our address>" for an address nothing actually negotiated doesn't mean much yet. The cache also has no eviction or TTL — a fixed-size table that just fills up.

The shell's arp command runs four checks in one pass, each independently checkable: resolve the gateway (a real external round trip, non-trivial elapsed ticks); resolve it again (zero elapsed ticks — a real, timing-based proof of the cache, not just "the same answer twice"); resolve a second, different real address (QEMU SLIRP's own DNS proxy, 10.0.2.3 — proving the resolver genuinely generalizes); and resolve an address nothing answers for (correctly returns false after the real timeout, not a hang). See the Walkthrough for the real captured output.

A real IP layer

A real IPv4 layer, verified with a genuine ICMP echo (ping) round trip — the minimal, natural test vehicle for "does IP genuinely work end to end." A bare IP packet with no upper-layer protocol has nothing that could reply to it; ICMP echo is the smallest real protocol that gets an external, independently meaningful response.

net/ip.c holds ip_checksum() (the real RFC 791 one's-complement checksum — sum every 16-bit word, fold any carry back in, take the complement; the identical algorithm also covers ICMP) and ip_build_header() (a real 20-byte, no-options IPv4 header). It also holds g_my_ip — this kernel's own first real, named concept of "my IP address." Previously a bare literal duplicated inside net/arp.c's own request-building code, it's now one shared value both files use (still a fixed, static assumption — 10.0.2.15, QEMU SLIRP's conventional default guest address — not real DHCP-negotiated configuration; see Known limitations).

net/icmp.c's icmp_ping() resolves the target's MAC via the real arp_resolve() first (a cache hit costs nothing here), builds a real Ethernet+IPv4+ICMP echo request, sends it, and polls — real g_tick_count- bounded, since a spin loop doesn't reliably correspond to real time — for a reply matching on every real field: EtherType, IP protocol, source IP, ICMP type, and the exact identifier/sequence number this specific request sent, not just "something ICMP arrived."

Verified in QEMU: ping gateway ok=0x1 elapsed_ticks=0x64 — a genuine reply from QEMU's real network stack, at the same non-trivial round-trip time arp already measured. A wrong IP header (a bad checksum, a malformed field) would most likely have gotten the packet silently dropped by QEMU's real host-level network stack rather than answered at all, so the reply arriving at all is itself strong indirect evidence the header was built correctly — the same "external validation beats self-validation" property every networking proof on this page looks for. See the Walkthrough for the real captured output.

A real UDP layer

UDP is the simpler of the two transport protocols: no connection state, no retransmission or congestion control, just a port-addressed datagram wrapper over the IP layer. TCP's real connection state machine, sequence numbers, and retransmission remain a substantially bigger, genuinely separate hard problem (see below).

net/udp.c's udp_checksum() covers a 12-byte "pseudo-header" (source IP, dest IP, a zero byte, the protocol number, and the UDP length) plus the real UDP header and payload — binding the checksum to the addresses it's actually being delivered between, unlike IP's own header checksum, which covers only the 20 header bytes. It reuses ip.c's ip_checksum() algorithm unchanged by assembling the pseudo-header and message into one scratch buffer first. udp_send()/udp_receive() follow the exact same resolve-then-send-then-poll shape icmp_ping() already established.

net/dns.c's dns_query() is the real external verification vehicle — deliberately not a real DNS client (no response caching, no compression-pointer decoding, no record types beyond A), the same "one hardcoded real-protocol message as a test vehicle" discipline ARP's request and ICMP's ping both already used. It sends a minimal, hand-crafted query to QEMU SLIRP's own built-in DNS proxy (10.0.2.3, the same address arp already resolves) and verifies the exact transaction ID sent, the response (QR) bit, and a real answer count — proving SLIRP genuinely forwarded the query to a real upstream resolver and got a real answer back.

Verified in QEMU: dns query ok=0x1 elapsed_ticks=0x74 — noticeably higher than ping's own elapsed_ticks=0x64, a real, sensible detail: DNS resolution genuinely takes one more hop than ICMP echo (SLIRP forwards the query out and waits for a real reply, rather than answering directly the way it does for ping) — exactly the kind of small, correct-shaped detail that would be hard to fake by accident. See the Walkthrough for the real captured output.

A real TCP client

TCP is the first genuinely stateful transport protocol in this kernel, and the only one that talks to a host off the local SLIRP subnet (every other protocol's target is the gateway at 10.0.2.2 or the DNS proxy at 10.0.2.3, both local). A real internet host doesn't answer ARP requests from this guest at all, so net/tcp.c's tcp_fetch() ARP-resolves the gateway's MAC for the Ethernet-level destination while putting the real remote IP in the IP header itself — routing, not resolution, decides an off-subnet frame's link-layer destination, the same distinction every real router relies on.

tcp_checksum() follows the identical pseudo-header shape udp_checksum() already established (protocol number 6 instead of 17). tcp_fetch() is deliberately scoped as a client only, one connection at a time, no connection table, no retransmission or congestion control — a real 3-way handshake (SYN, wait for a genuinely matching SYN-ACK with the right ACK number, then ACK), a real data segment carrying an actual HTTP/1.1 request, a receive loop that ACKs each arriving segment and keeps polling until the peer's FIN or the caller's buffer fills, and a best-effort graceful close that isn't required for a successful fetch to have already happened. net/dns.c gained a real dns_resolve_a() alongside the existing dns_query() — it actually parses the answer section (a DNS-compression name pointer or a literal one, skipping past a CNAME if one leads) instead of only checking the header, so the TCP demo's target is a freshly-resolved real IP, not a hardcoded address that could go stale. No retransmission, congestion control, listening/server side, or connection table — real, substantial follow-on work, not oversights.

Verified in QEMU, twice, independently: two different real IPs for example.com (Cloudflare's own round-robin DNS, both confirmed via a real curl from the same environment) — tcp_fetch_ok=0x1 response_len=0x200 got_http_status=0x1 both times, a complete handshake, a full 512-byte real HTTP response (the receive buffer's own cap — the real reply was at least that long), and a confirmed real HTTP status line at the start of it, not just "some bytes arrived." tasks run immediately afterward confirmed the scheduler and every other kernel task stayed healthy through the exchange. See the Walkthrough for the real captured output.

Testing methodology

Every claim in this project is backed by a concrete, checkable assertion — never just "it didn't crash." An exact byte count matching hand arithmetic, a register value read back and printed (proving real CPL 3, not just "a syscall happened"), a physical address that genuinely differs between two isolated processes mapping the identical virtual address, a frame-allocator count identical before and after an operation that must not leak. See the Walkthrough for what these look like in practice.

Testing runs in QEMU, headless, with serial output redirected to a file and keystrokes sent over the monitor socket: 

qemu-system-x86_64 -kernel kernel.elf -display none \
    -serial file:serial.log -monitor unix:/tmp/qmon,server,nowait \
    -drive file=disk.img,format=raw,if=ide -no-reboot
echo 'sendkey h' | nc -U /tmp/qmon   # types 'h'
echo 'sendkey spc' | nc -U /tmp/qmon # space
echo 'sendkey ret' | nc -U /tmp/qmon # enter

Known limitations (on purpose, for now)

  • Pointer arguments (paths, buffers) are checked for validity/bounds but not ownership — nothing stops a ring3 process from passing a pointer that doesn't actually belong to it. channel and process handles are real, rights-checked capabilities (see Capabilities & rights) — but process only has one real right (RIGHT_QUERY) to enforce so far, since there's no second Process operation (like a real terminate/kill) yet to need a second one. unregister_service (see Process model & isolation) shares this same gap: any process can unregister any runtime service slot, not just the one it registered.
  • A handle another process holds to a still-running process can be released early (handle_close) and everything tied to an exited process is reclaimed (frames, process/task slot, kernel object table) — see Process model & isolation for the full mechanism. Still open: any handle still pointing at an exited-then-reused process slot now points at a different, live process, not just a frozen dead one - a sharper, more real version of the pointer-ownership gap above.
  • init.c restarts its one service exactly once per cycle, not in an unbounded loop — a real restart-on-exit proof, but not a real supervisor: no restart limit/backoff, no dependency ordering, and a second restart would fail outright once the fixed 4-slot process table fills.
  • Async file I/O (see Async file I/O) is backed by a fixed pool of 4 pending-request slots with a 512-byte buffer each — an operation larger than that gets silently truncated to the buffer's capacity, same as any other fixed-size table in this kernel. Async networking (see Async networking) covers ICMP ping and DNS A-record resolution only, from a separate 2-slot pool shared between the two — no async ARP/UDP/TCP for ring3 yet, and those protocols still have no ring3-facing syscall at all (they remain kernel-mode shell commands only).
  • A loaded ring3 program's own code+data image is fully executable (no W^X split within it — the loader flattens a whole compiled program into one contiguous blob with no tracked code/data boundary, so NX protection, which does cover every dynamically-mapped pure-data region including every ring3 process's own user stack, can't be applied within a loaded image itself; see Memory protection). ASLR and true process sandboxing (beyond the address-space isolation this kernel already has) remain two more genuinely different, completely unscoped mechanisms — not silently forgotten, just not yet tackled.
  • Every fixed-size table in this kernel (tasks, processes, objects, handles, channels, mounts) has a small, arbitrary capacity, and most creation calls at boot don't check their own return value for success — harmless today (nothing is near its cap), a real bug class once boot-time setup grows further.
  • MiniFS is deliberately simple — flat namespace (no directories), a fixed 16-file cap, no delete/truncate/append, no journaling (a crash mid-write leaves partial state), and files can't safely be overwritten (only created fresh).
  • The ATA driver only supports the primary bus's master drive, polling rather than interrupt-driven — no secondary bus, no slave, no AHCI/NVMe.
  • PCI enumeration is bus 0 only (see Hardware discovery: PCI) — no bridge recursion, no general driver-registration framework. disk/ata.c also hasn't been retrofitted to use PCI discovery instead of its own hardcoded 0x1F0, even though pci finds that exact same controller.
  • ARP is client-only (no responder), with no cache eviction/TTL. This kernel's own IP address (g_my_ip) is a fixed, static assumption, not real DHCP-negotiated configuration. ICMP is the only IP-layer protocol implemented, and only its echo request/reply message type at that. net/dns.c's dns_query() is deliberately not a real DNS client — no caching, no record types beyond A — it exists purely as an external test vehicle for UDP (dns_resolve_a(), used for TCP's own target resolution, does real answer-section parsing but still only ever asks for one A record, no retry, no multiple questions). TCP (see A real TCP client) is client-only, one connection at a time with no connection table, no retransmission or congestion control at all (a lost segment just times out), no options (no window scaling, no SACK), and close is best-effort only. The e1000's TX/RX rings are fixed-size (8 descriptors each), and both poll rather than using the device's own interrupt capability — the same "poll first, interrupts later" precedent disk/ata.c already established.
